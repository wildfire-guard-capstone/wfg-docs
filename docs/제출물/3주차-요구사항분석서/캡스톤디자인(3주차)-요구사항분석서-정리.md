### 한 단락 요약

본 분석서는 산불 발생 직후부터 진화·대피 판단이 이어지는 8시간 안팎의 대응 과정에서, 산불현장 통합지휘권자(시장·군수·구청장)에게 통합 상황도와 판단 항목별 대응 제안서를 「산불 재난」 위기관리 표준매뉴얼 근거와 함께 제공하는 웹 대시보드의 요구사항을 정의한다. 시스템은 물리 엔진(ELMFIRE)으로 1시간 간격 누적 확산 범위 P1~P8을 예측하고, 규칙 엔진(Rule-Based)이 근거 문서에 경계값·수치가 있는 값(대응단계·위험구역·대피소 배정 등)을 판정하며, 국내 LLM(EXAONE 4.0 32B) 위의 에이전트 2개(상황판단·어시스턴트)가 진화 7개(S1~S7)·대피 7개(E1~E7) 판단 항목별 제안 문장을 KURE-v1 + FAISS 근거 검색 결과를 인용해 작성한다. 사용자는 통합지휘권자·열람자·상황 보고자·전산 관리자 4개 권한으로 나뉘며, 유스케이스 15개(UC-AUTH/REPORT/SIT/PRED/PROP/QA/ADMIN), 기능 32개(F-01~F-32), 도메인 엔티티 18개와 논리 컴포넌트 18개, 관계형 DB 관계와 의성 2025-03-22 시나리오 예시 데이터, 비기능 요구사항 23개(INR/ECR/PER/SER/LGR/QUR/ORP/DPR/TER)와 AI 성능 목표(IoU ≥ 0.50, Recall@5 ≥ 0.80, 충실도 ≥ 0.90, 관련성 ≥ 0.80)를 기술한다. 운영 원칙은 "AI는 근거 있는 초안을 제시하고 최종 결정은 통합지휘권자가 내린다"이다.

## 02. 시스템 기술서 (슬라이드 9~13)

> **발표 설명 (대본①, 2분 배정)** — 절차는 네 문장: ① 발화 정보·실측 화선·기상으로 1시간 간격 확산 예측, ② 규칙 엔진이 경계값 있는 판정 값 계산, ③ EXAONE이 그 값과 상황 데이터로 진화 7·대피 7 제안을 쓰며 근거 인용, ④ 통합지휘권자가 어시스턴트로 묻거나 상황을 정정해 제안을 다시 받음. 권한은 조작·열람·보고·관리 네 가지, 열람자는 상황도와 발생·접수 정보만. "확산대응 2단계 격상 시 지휘권 인계를 안내하고, 종료된 산불은 수정·예측·정정을 차단하며, 모든 이벤트는 추가 전용 로그에 남습니다." 업무 절차 흐름은 로그인 → 상황 보고 → 상황 확인 → 확산 예측 → 규칙 판정과 제안 생성 → 새 버전 저장 → 제안 검토와 질의·정정 → 종료 처리의 여덟 단계. "예측은 통합지휘권자가 실행할 때만 돌고, 정정은 예측을 유지한 채 판정과 제안만 다시 합니다." 기능 32개 중 "대응 제안 18개, 공통 4개와 진화 7·대피 7이 핵심".

### 2.1 절차 기술 (슬라이드 9)

원문 6개 단락(그대로 옮김):

1. 본 시스템은 산불 확산 예측 결과를 「산불 재난」 위기관리 표준매뉴얼 근거와 연결해, 산불현장 통합지휘권자에게 지금 해야 할 진화·대피 조치를 제안하는 의사결정 지원 웹 시스템이다. 최근 산불은 발생 건수가 줄어도 한 번의 피해가 커지고 있으나, 기존 국가 시스템은 확산 예측과 위험도를 제공할 뿐 그 결과를 어떤 대응 행동으로 옮길지는 소수 인력이 119쪽 분량의 매뉴얼을 찾아 가며 수작업으로 판단하고 있다.

2. 이를 해결하기 위해 시스템은 ① 현장에서 입력된 발화 정보·실측 화선과 기상으로 1시간 간격 확산 범위를 예측하고, ② 규칙 엔진이 예측 결과로 대응단계·위험구역·대피소 배정처럼 근거 문서에 경계값·수치가 있는 판정 값을 계산한 뒤, ③ 국내 LLM(EXAONE 4.0 32B)이 그 판정 값과 상황 데이터를 넘겨받아 진화 7개(S1~S7)·대피 7개(E1~E7) 항목의 대응을 판단해 제안 문장을 만들고 RAG로 검색한 매뉴얼 근거를 인용하며, ④ 통합지휘권자가 AI 어시스턴트로 제안 이유와 근거를 묻거나 대피 완료 같은 상황 변화를 알려 제안을 다시 받게 한다. 경계값이 있는 수치 판정은 규칙이 맡고 LLM은 그 값을 바꾸지 못하며, 제안 문장마다 근거를 붙여 근거 없는 판단을 만들지 않도록 한다.

3. 사용자는 네 가지 권한으로 나뉜다. 통합지휘권자는 초기대응·확산대응 1단계에서 통합지휘본부장이자 주민대피 명령권자인 시장·군수·구청장이다(p.72, p.84). 확산대응 2단계로 격상되면 지휘권 인계를 안내한다(S6). 확산 예측을 실행해 대응 제안을 만들고, 위험도와 제안·근거를 검토하며, AI 어시스턴트에 질문하거나 상황을 정정하고, 진화가 끝나면 발화 종료 처리를 한다. 열람자는 유관기관·상급 본부 담당자로 통합 상황도와 발생·접수 정보를 보기만 한다. 상황 보고자는 초기 발화 위치·일시와 진행 중인 실측 화선을 폴리곤으로 입력하고, 전산 관리자는 평시에 계정·권한과 진화자원 데이터를 관리한다. 로그인에 5회 연속 실패해 잠긴 계정은 전산 관리자만 잠금 해제하며, 해제 시 실패 횟수를 0으로 초기화한다.

4. 시스템 측 참여자는 확산예측 모듈(ELMFIRE), AI 모델(EXAONE + KURE-v1 근거 검색), 기상청 API·공공데이터(단기예보, 위성영상·지도 타일, SGIS 경계, 마을·시설·대피소·도로)다. 확산예측 모듈이 최신 실측 화선(없으면 발화점)에서 30 m 격자의 지형·연료와 기상으로 누적 확산 범위 P1~P8을 만들면, 시스템은 이를 공간 DB에 저장해 지도 표시·규칙 판정·제안 생성에 함께 쓴다. 로그인·로그아웃·입력·예측·제안·정정·종료·계정 및 자원 변경 이벤트는 추가 전용 이벤트 로그에 기록되고, 제안 이력 화면에서 시각·구분·내용·사용자 기준으로 읽기 전용 열람한다.

5. 업무 절차는 다음과 같다. 상황 보고자가 발화 정보와 실측 화선을 입력하면 통합지휘권자와 열람자는 통합 상황도에서 확산 범위, 주요 시설의 위치, 진화자원을 확인한다. 통합지휘권자가 확산 예측을 실행하면 시스템은 예측을 저장한 뒤 곧바로 진화·대피 제안서를 만든다. 제안은 즉시·대기·협의·요청으로 구분되며 모든 문장 끝에 근거 번호가 붙는다. 예측이 갱신되거나 상황 정정이 확정되면 새 버전이 생기고 바뀐 항목이 표시되며, 진화가 끝나면 통합지휘권자가 발화 종료 처리를 한다. 종료 후에는 발화 정보 수정, 예측 실행, 상황 정정, 제안 재생성을 차단하고 기존 제안은 이력으로만 열람한다.

6. 이로써 예측과 대응 사이의 수작업 공백을 줄이고 판단 근거를 조항 단위로 추적할 수 있는 투명한 의사결정 환경을 제공한다. 시스템은 권고만 하며, 대응단계 발령과 대피명령 같은 최종 결정은 통합지휘권자가 내린다.

## 03. 유스케이스 다이어그램 (슬라이드 14~33)

> **발표 설명 (대본①, 3.5분 배정 — 가장 긴 장)** — 액터는 사람 넷, 시스템 셋. 상황 보고자를 따로 둔 이유는 "1시간마다 실측 화선이 들어와야 재예측이 성립하기 때문". 다이어그램(16쪽)은 오른쪽 주요 흐름 여섯 단계로 설명: ① 평시 전산 관리자가 계정·진화자원 준비 → ② 상황 보고자가 보고하면 통합지휘권자가 발생·접수 정보와 상황도 확인 → ③ 위험도 보고 확산 예측 실행 → 제안서 생성 → ④ AI에 묻고 상황 정정하면 제안서 재생성 → ⑤ 1시간마다 새 실측 화선이 오면 「다시 예측」으로 새 버전 → ⑥ 진화 끝나면 종료. "관계는 근거 조회·이력 조회처럼 필요할 때만 붙는 extend 다섯 개이고, 유스케이스는 재난 시 13개, 평시 2개, 모두 15개." include가 없는 이유는 "예측과 제안 생성을 사용자 입장에서 한 유스케이스로 묶었기 때문". 시나리오 15장 중 발표에서 짚은 4장: 20쪽 산불 상황 보고(출발점), 24쪽 확산 예측·대응 제안 생성(핵심 기능), 29쪽 AI 상황 정정, 30쪽 제안 이력.
>
> (대본②) 27쪽 근거 조회를 25~26쪽보다 오래 머무는 장으로 지정: "사용자가 이 번호를 누르면 해당 내용이 어떤 문서의 몇 페이지, 어떤 조항에 근거했는지를 확인할 수 있습니다." 28쪽: "일반 질문은 기존 상황이나 제안을 변경하지 않습니다." 29쪽: "상황 변화가 입력되면 AI가 이를 바로 반영하지 않습니다. 먼저 변경할 내용을 사용자에게 보여주고, 확인 후 저장합니다."

(슬라이드 14는 "03. 유스케이스 다이어그램" 구분 슬라이드)

#### UC-AUTH-01 로그인 (슬라이드 19)

| 항목 | 내용 |
|---|---|
| 개요 | 사용자가 전산 관리자에게 발급받은 계정으로 인증하고, 권한(조작·열람·보고·관리)에 맞는 첫 화면으로 들어간다. 회원가입은 없다 |
| 액터 | 통합지휘권자, 열람자, 상황 보고자, 전산 관리자 |
| 시작 조건 | 전산 관리자가 계정과 권한을 미리 발급해 두었다 (UC-ADMIN-01) |
| 기본 흐름 | 1. 사용자가 로그인 화면에서 사용자 구분(통합지휘권자·열람자·상황 보고자·전산 관리자)을 고르고 발급받은 아이디·비밀번호를 입력한 뒤 「로그인」을 누른다.<br>2. 시스템이 계정의 잠금 여부를 먼저 확인하고, 계정 정보와 비밀번호를 대조해 인증하며, 선택한 구분이 계정 권한과 일치하는지와 계정이 회수되지 않았는지 확인한다.<br>3. 시스템이 계정에 지정된 권한을 담은 JWT(로그인 상태와 권한을 증명하는 서명된 토큰)를 발급해 세션에 적용한다.<br>4. 시스템이 권한별 첫 화면을 띄운다 — 통합지휘권자·열람자는 진행 중 산불의 통합 상황도, 상황 보고자는 상황 입력 화면(지도 + 상황 입력 판), 전산 관리자는 계정·진화자원 데이터 관리 화면. |
| 대안 흐름 | A1. 유효한 토큰이 남아 있을 시 → 로그인 없이 권한별 첫 화면으로 바로 진입<br>A2. 「로그아웃」을 누를 시 → 세션 토큰을 폐기하고 로그인 화면으로 돌아감 |
| 예외 흐름 | E1. 아이디·비밀번호가 맞지 않거나 선택한 구분이 계정 권한과 다르면 시스템이 "아이디 또는 비밀번호가 올바르지 않습니다"를 표시하고 실패 횟수를 1 올린 뒤 다시 입력받는다.<br>E2. 회수된 계정이면 시스템이 로그인을 막고 전산 관리자에게 문의하라고 안내한다.<br>E3. 5회 연속 실패하면 시스템이 계정을 잠그고 "계정이 잠겼습니다. 전산 관리자에게 문의하세요"를 표시한다. 잠긴 계정은 전산 관리자가 잠금 해제한다(UC-ADMIN-01). |
| 종료 조건 | JWT가 발급되어 권한이 적용된 세션이 만들어지고, 권한에 맞는 첫 화면이 표시된다 |

#### UC-REPORT-01 산불 상황 보고 (슬라이드 20)

| 항목 | 내용 |
|---|---|
| 개요 | 상황 보고자가 산불을 처음 보고할 때 발화 위치·발생 날짜·시각·신고 내용·접수 시각·접수 기관을 입력해 산불 사건을 시작하고, 이후 1시간마다 실측 화선(지금 타고 있는 범위를 그린 폴리곤)을 보고한다. 이 실측 화선이 재예측·제안 재생성의 출발점이며, 초기대응처럼 아직 화선이 없으면 발화점에서 예측한다. |
| 액터 | 상황 보고자 |
| 시작 조건 | 상황 보고자가 '보고' 권한 계정으로 로그인한 상태 (UC-AUTH-01) |
| 기본 흐름 | 1. 상황 보고자가 상황 입력 화면(지도 + 상황 입력 판)에서 「새 산불 보고」를 누른다.<br>2. 상황 보고자가 지도에 발화 지점을 찍고 발생 일시·신고 내용·접수 시각을 입력하고, 기관별 접수 기록(접수 기관·접수 시각·접수 경로)을 추가한다.<br>3. 상황 보고자가 지금 타고 있는 범위를 실측 화선 폴리곤으로 그려 제출한다(초기대응에서 화선이 없으면 생략 가능).<br>4. 시스템이 입력값을 검증하고 산불을 '접수' 상태로 생성해 발화 정보를 저장한다. 실측 화선이 함께 제출되면 화선 버전 1을 저장하고, 실측 화선이 처음 저장되는 시점에 상태를 '진행 중'으로 바꾼다.<br>5. 시스템이 발생·접수 정보(UC-SIT-02)와 통합 상황도(UC-SIT-03)에 새 산불의 발화점과 실측 화선을 표시한다. |
| 대안 흐름 | A1. 1시간 주기 보고 시 → 직전 실측 화선을 불러와 수정 후 새 버전(v2, v3…)으로 제출<br>A2. 잘못 보고한 실측 화선 정정 시 → 수정본을 다시 제출, 이전 버전은 '정정됨'으로 보존 |
| 예외 흐름 | E1. 입력한 산불 정보(발화 지점·시각·실측 화선)가 올바르지 않으면 시스템이 제출을 막고 잘못된 항목을 표시한다.<br>E2. 종료 처리된 산불에는 시스템이 보고를 받지 않는다(UC-SIT-01). |
| 종료 조건 | 산불 사건이 '접수' 또는 '진행 중'(실측 화선이 처음 저장되면 진행 중)으로 존재하고, 발화 정보와 최신 실측 화선(버전 포함)이 저장되어 상황판·예측의 입력으로 쓰인다 |

#### UC-SIT-02 산불 발생·접수 정보 조회 (슬라이드 21)

| 항목 | 내용 |
|---|---|
| 개요 | 사용자가 예측이 아닌 지금 상황 — 어디서 났고, 누가 언제 신고했고, 지금 어떤 상태인지 — 를 확인한다 |
| 액터 | 통합지휘권자, 열람자, 상황 보고자 |
| 시작 조건 | 로그인 상태, 상황 보고자가 산불을 1건 이상 보고함 (UC-REPORT-01) |

| 대안 흐름 | A1. 목록 보기를 「종료」로 바꿀 시 → 종료 처리된 산불 목록 표시<br>A2. 상황 보고자일 시 → 「실측 화선 보고」 버튼으로 UC-REPORT-01(A1) 진행 |
| 예외 흐름 | E1. 접수·진행 중인 산불이 없으면 시스템이 "진행 중인 산불이 없습니다"를 표시한다. |
| 종료 조건 | 선택한 산불의 발생·접수 정보와 진행 상태가 표시된다 |

#### UC-SIT-03 통합 상황도 조회 (슬라이드 22)

| 항목 | 내용 |
|---|---|
| 개요 | 지도 한 장 위에 발화점·실측 화선·확산 폴리곤(예상 확산 범위 도형)과 마을·시설·진화자원을 겹쳐, "불이 어디까지 오고 그 안에 무엇이 있는지"를 본다. |
| 액터 | 통합지휘권자, 열람자 / 기상청 API·공공데이터 |
| 시작 조건 | 로그인 상태, 등록된 산불 1건 이상 |
| 기본 흐름 | 1. 사용자가 통합 상황도를 연다(로그인 후 첫 화면 또는 UC-SIT-02에서 산불 선택).<br>2. 시스템이 공공데이터 기반 지도 위에 발화점과 상황 보고자가 입력한 실측 화선을 그린다. 예측 결과가 있으면 1시간 간격 확산 범위 P1~P8을 겹치고, 위험구역(P5, 5시간 내 도달 범위)과 잠재 위험구역(P8, 8시간 내)을 색을 달리해 강조한다.<br>3. 시스템이 마을·담수지·유관기관 등 주요 시설 위치를 아이콘으로 표시한다(발화점과의 거리는 표시하지 않음).<br>4. 사용자가 레이어 패널에서 인구·시설·도로·기관 레이어를 켜고 끄면 시스템이 즉시 지도에 반영한다.<br>5. 사용자가 시간 재생(t = 1 … 8)을 누르면 시스템이 해당 시점의 확산 범위 P(t)를 채우고 도달한 마을을 강조한다.<br>6. 사용자가 「진화자원」 패널을 열면 시스템이 진화자원 데이터(UC-ADMIN-02)를 바탕으로 헬기·인력·차량 현황을 표시한다. 기본은 「가용만 보기」 필터이며, 필터를 끄면 보유·투입·대기까지 모두 표시한다. |
| 대안 흐름 | A1. 예측 전일 시 → 발화점·실측 화선·시설만 표시 (P1~P8 없음)<br>A2. 종료된 산불일 시 → 예측 범위(P1~P8) 없이 발화점과 보고된 실측 화선만 표시 |
| 예외 흐름 | E1. 공공데이터·기상 데이터 호출에 실패하면 시스템이 마지막으로 받은 값과 수신 시각을 함께 표시한다. |
| 종료 조건 | 실측 화선·예측 범위(P1~P8), 주요 시설, 진화자원 현황(가용만 보기 필터)이 겹쳐진 상황도가 표시된다 |

#### UC-PRED-02 산불 위험도 확인 (슬라이드 23)

| 항목 | 내용 |
|---|---|
| 개요 | 통합지휘권자가 발화 지점이 얼마나 위험한 조건인지(조건위험도 0~100, 등급, 요인별 기여)를 확인해 예측과 함께 판단 재료로 쓴다. 시스템은 산불별 최대 위험도를 저장해 종료 후에도 보여준다 |
| 액터 | 통합지휘권자 / 기상청 API·공공데이터 |
| 시작 조건 | 통합지휘권자로 로그인, 발화 정보가 입력된 상태 (UC-REPORT-01) |
| 기본 흐름 | 1. 통합지휘권자가 상황도의 「위험도」를 연다.<br>2. 시스템이 발화 지점의 기상(기상청 API)과 지형·연료·인프라(공공데이터) 값을 보여준다.<br>3. 시스템이 요인별 점수를 합산해 조건위험도(0~100)와 등급(낮음·보통·높음·매우 높음)을 계산하고, 산불별 최대 위험도를 갱신·저장한다.<br>4. 시스템이 점수·등급과 요인별 기여도(기상·지형·연료·인프라가 각각 얼마나 위험을 올렸는지)를 막대로 표시한다. |
| 대안 흐름 | A1. 발화 정보나 기상 값이 바뀔 시 → 위험도 재계산, 최대 위험도보다 높으면 갱신<br>A2. 종료된 산불일 시 → 저장된 최대 위험도·등급·요인을 표시 |
| 예외 흐름 | E1. 필수 변수가 없으면 시스템이 "위험도 계산 실패"를 안내하고 재시도 창을 띄운다.<br>E2. 일부 변수만 결측이면 시스템이 결측 변수를 빼고 계산하고 결측 목록을 함께 표시한다.<br>E3. 기상청 API 호출에 실패하면 시스템이 마지막으로 받은 기상 값과 수신 시각을 표시한다. |
| 종료 조건 | 위험도 점수·등급·요인이 표시되고, 산불별 최대 위험도가 저장된다 |

#### UC-PRED-01 확산 예측 실행·갱신 → 대응 제안(진화, 대피) 생성 (슬라이드 24)

| 항목 | 내용 |
|---|---|
| 개요 | 최신 실측 화선(없으면 발화점)을 시작점으로 1시간 간격 누적 확산 범위 P1~P8을 예측하고, 그 결과로 진화 7항목·대피 7항목 대응 제안서를 새 버전으로 만든다. 재예측은 통합지휘권자가 버튼을 누를 때만 실행되며, 누른 시점의 최신 실측 화선·기상·자원 상태를 기준으로 한다(자동 실행 없음) |
| 액터 | 통합지휘권자 / 확산예측 모듈, AI 모델 (기상은 기상청 API) |

## 04. 시퀀스 다이어그램 (슬라이드 34~48)

> **발표 설명 (대본①, 2분 배정)** — 공통 원칙: "요청마다 권한과 상태를 먼저 검사하고, 종료된 산불은 차단하고, 오류 시 기존 데이터를 유지하고, 상태 변경은 로그에 추가 전용으로 남기는 것." 열네 장 중 세 흐름만 설명. 로그인(35쪽)은 잠금·회수 여부 → 비밀번호·구분 검사 → JWT, 5회 실패 시 잠금. 상황 보고(36쪽)는 종료 여부·보고 권한·필수 값·좌표·폴리곤 검사 후 PostGIS 저장. 확산 예측 ①②(40~41쪽): 발화점·최신 실측 화선·기준 시각 검증 → 단기예보 → ELMFIRE → P1~P8 누적성 검사 → 저장. 이어 제안 오케스트레이터가 규칙 엔진으로 판정 값과 발동 항목을 정하고, "항목마다 질문 작성, 근거 5개 검색, 근거 인용 답변, 충돌 검사, 종합 순으로 EXAONE을 호출해 인용 번호를 검증한 뒤 새 버전으로 저장. 예측이 실패하면 이전 결과를, 제안 생성만 실패해도 직전 묶음을 유지." AI 상황 정정(46쪽)은 확인 창 → 확인한 경우에만 저장 → 판정과 제안만 재수행.
>
> (대본②) 41쪽 한 줄 요약: "규칙 판정, 근거 검색, AI 생성, 검증의 순서." 45쪽: "AI 입력은 먼저 일반 질문인지 상황 변화인지를 구분합니다."

(슬라이드 34는 "04. 시퀀스 다이어그램" 구분 슬라이드. 이하 각 다이어그램은 도형으로 그려져 있어 참여자(라이프라인)와 메시지 라벨, alt/opt/loop 프레임을 순서대로 옮겼다. 메시지 순서는 슬라이드 내 텍스트 상자 순서를 따른다.)

### 4.1 로그인 (UC-AUTH-01) (슬라이드 35)

참여자: 사용자 · 프론트엔드 · AuthRouter · SecurityService · DB · EventLogger

1. 사용자 → 프론트엔드: 아이디·비밀번호 입력, 사용자 구분 선택, 로그인
2. 프론트엔드 → AuthRouter: `POST /auth/login (id, pw, 구분)`
3. AuthRouter → DB: 계정 조회(login_id) / DB → AuthRouter: 해시·role·상태·잠금여부(발급/회수)
4. AuthRouter → SecurityService: 잠금 여부 우선 확인 → verify_password() · 구분 일치 확인 / SecurityService → AuthRouter: 검증 결과
5. **alt**
   - [잠긴 계정]: AuthRouter → 프론트엔드: 423 「계정이 잠겼습니다」 → 사용자: 잠금 안내 표시(전산 관리자 문의)
   - [불일치·구분 다름]: AuthRouter → DB: 실패 횟수 +1(5회 도달 시 계정 잠금) · 상태 저장 → 프론트엔드: 401 「아이디 또는 비밀번호가 올바르지 않습니다」 → 오류 메시지 표시
   - [회수 계정]: AuthRouter → 프론트엔드: 403 「회수된 계정입니다」 → 오류 메시지 표시
   - [일치]: AuthRouter → SecurityService: create_token(role, 관할) / SecurityService → AuthRouter: JWT; AuthRouter → EventLogger: record(시스템, 로그인 · 실패횟수 초기화); AuthRouter → 프론트엔드: 200 token · role; 프론트엔드: 권한별 첫 화면 구성(조작·열람·보고·관리) → 사용자: 첫 화면 표시

### 4.2 산불 상황 보고 (UC-REPORT-01) (슬라이드 36)

참여자: 상황 보고자 · 프론트엔드 · IncidentRouter · DB(PostGIS) · EventLogger

1. 상황 보고자 → 프론트엔드: 산불 선택 / 새 산불, 발화 위치 지도 지정
2. 상황 보고자 → 프론트엔드: 발생·접수 일시, 신고 내용, 접수 기관·경로 입력
3. 상황 보고자 → 프론트엔드: 실측 화선: 지도에서 그리기 → 그리기 완료 (또는 GeoJSON) / 프론트엔드: 꼭짓점 수 · 면적(ha) 표시
4. 상황 보고자 → 프론트엔드: 「저장」 / 프론트엔드 → IncidentRouter: `PUT /incidents/{id} (발화 정보 + 실측 화선 GeoJSON)`
5. IncidentRouter: 산불 종료 여부 확인 / 권한(보고)·필수 값·국내 좌표 범위·폴리곤 검사
6. **alt**
   - [종료된 산불]: 409 「종료된 산불은 수정할 수 없습니다」 → 프론트엔드: 안내, 저장 안 함
   - [검사 실패]: 400 필요한 항목·이유 → 안내, 저장 안 함
   - [정상]: IncidentRouter → DB: 산불 저장(첫 실측 화선 저장 시 접수→진행 중); IncidentRouter → EventLogger: record(입력, 발화정보 갱신); IncidentRouter → 프론트엔드: 저장 결과 · 면적 · 재예측 필요 여부; 프론트엔드: 목록 갱신, 지도에 실측 화선 표시

### 4.3 발화 종료 처리 (UC-SIT-01) (슬라이드 37)

참여자: 통합지휘권자 · 프론트엔드 · IncidentRouter · DB · EventLogger

1. 통합지휘권자 → 프론트엔드: 「종료 처리」 / 프론트엔드: 확인 창(종료 시각 · 이후 변경 차단 안내)
2. **alt**

   - [「취소」]: 변경 없음

### 4.4 산불 발생·접수 정보 조회 (UC-SIT-02) (슬라이드 38)

### 4.5 통합 상황도 조회 (UC-SIT-03) (슬라이드 39)

참여자: 사용자 · 프론트엔드 · 지도 타일 서버 · MapRouter · DB(PostGIS)

2. 프론트엔드 → 지도 타일 서버: 위성영상·라벨 타일 요청 / ← 타일
3. 프론트엔드 → MapRouter: `GET /incidents/{id}/map?layers=…`; MapRouter → DB: 실측 화선·P1~P8·시설·기관·기상 캐시 조회 / ← 공간 객체; MapRouter → 프론트엔드: GeoJSON

7. 프론트엔드 → 사용자: 통합 상황도 표시

### 4.6 확산 예측 실행 · 갱신 ① (UC-PRED-01) (슬라이드 40)

1. 통합지휘권자 → 프론트엔드: 확산 예측 실행 / 다시 예측
2. 프론트엔드 → PredictionRouter: `POST /incidents/{id}/predictions`; PredictionRouter: 권한(조작) 확인 → PredictionService: execute(incident, perimeter?)
3. PredictionService: 입력 검증(발화점·실측 화선·t0) → 단기예보 조회(WeatherClient) → ELMFIRE 실행(ElmfireAdapter, 초기 화선·격자·기상) → P1~P8 폴리곤 변환·누적성 검증
4. **alt**
   - [성공]: PredictionService → DB: 예측 실행·슬라이스 저장; → EventLogger: record(예측, 확산 예측 갱신); PredictionService: 대응 제안 생성 호출(→② 제안 생성); → PredictionRouter: P1~P8 새 버전 정보(GeoJSON); → 프론트엔드: 예측 결과 전달; 프론트엔드: 진행단계·화선 갱신
   - [실행 실패]: 오류, 이전 결과 유지 (PredictionService → Router → 프론트엔드)

### 4.7 확산 예측 → 대응 제안(진화 · 대피) 생성 ② (UC-PRED-01) (슬라이드 41)

참여자: 제안 오케스트레이터 · 규칙 엔진 · 근거 검색 · AI 모델(EXAONE) · DB · EventLogger

1. 제안 오케스트레이터 → 규칙 엔진: evaluate(예측·현재 상황·정정 값); 규칙 엔진 → DB: 공간 교차·도달 슬라이스 / ← 교차 결과; 규칙 엔진 → 오케스트레이터: 판정 값(단계·위험구역·배정 등)

### 7.3 비기능 요구사항(AI) — AI 성능 목표 (잠정 내부 목표) (슬라이드 102)

| 목표치 | 지표 | 설명 |
|---|---|---|
| ≥ 0.50 | 확산 예측 IoU | 예측 경계 ∩ 실측 소실 경계 ÷ 합집합 / hold-out 산불 사건 기준 |
| ≥ 0.80 | 근거 검색 Recall@5 | 정답 청크가 상위 5개 안에 드는 비율 / (nDCG@5 함께 보고) |
| ≥ 0.90 | 제안 충실도 | 제안·답변 주장이 검색 근거로 뒷받침되는 비율 (RAGAS) |
| ≥ 0.80 | 답변 관련성 | 제안·답변이 질문과 상황에 맞는 정도 (RAGAS) |

- 측정 대상: hold-out 산불 사건(보정 미사용)
- 비교 기준: 같은 질의·사건에서 RAG 유무 절제 실험
- 채점 방식: 로컬 EXAONE 채점 프롬프트(휴먼 평가 없음)
- ※ 자동 지표는 대리 지표이며 현장 유효성 입증과 구분합니다. 목표치는 수정 과제계획서 5.4의 잠정 내부 목표이며, 외부 LLM으로 데이터를 보내지 않습니다.
