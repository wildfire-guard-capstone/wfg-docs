### 읽기 전에: 두 문서의 성격 차이

2주차는 **과제계획서**(무엇을 왜 만들 것인가, 데이터·모델 선정 근거, 일정·협업)이고 3주차는 **요구사항 분석서**(기능 목록·유스케이스·시퀀스·클래스·DB·비기능 요구사항)다. 그래서 3주차에 새로 나타나는 내용 대부분은 "설계 수준이 깊어진 것"이지 "계획을 뒤집은 것"이 아니다. 아래 정리에서는 이 둘을 구분하려고 했다. 반대로 2주차에 있던 데이터 분석(4장), 모델 선정 비교(표 5-1), 협업 체계(6.3), 기대효과 상세(7장)는 3주차 문서 범위 밖이라 "삭제"로 읽지 않는다.

## 1. 출력 대상과 역할 체계 [대본 명시]

### 2주차

- 과제명 부제: "역할별 대응 임무 생성 플랫폼".
- 2.2 "소방·구조·행정 각 역할이 지금 수행해야 할 임무를 자동 작성". 5.2.2.1 역할 3종 FF/RW/GO, 각 역할 아래 검색 대상 기관 목록([표 5-2]). 5.2.2.2 대응 단계·행정구역 경계로 역할 활성화 기관을 규칙 판정([표 5-3], 예규 별표 1).
- 보고서 구성([표 5-5]): 현장 분석(공통) + 소방요원 질의 3 · 구조요원 질의 3 · 공무원 질의 4.
- 표출(5.3): "역할(FF/RW/GO) 탭별로 현장 분석과 임무 목록".
- 아키텍처 그림의 사용자 박스: 「사용자(현장 역할)」 FF·RW·GO.

### 3주차

- 표지 부제: "산불 확산 예측과 표준매뉴얼 근거 기반 진화·대피 대응 제안".
- 슬라이드 3 정의: "재난관리주관기관은 산림청, 현장 통합지휘와 주민대피 명령권자는 시장·군수·구청장(재난안전법 시행령 별표 1의3 · 산림재난방지법 제34조)". 출력 A 대응 제안서 = 진화 7 · 대피 7 판단 항목별 대응안.
- 사용자 4권한(슬라이드 9·15): 통합지휘권자(조작) / 열람자(열람, 유관기관·상급 본부) / 상황 보고자(보고) / 전산 관리자(관리). RoleEnum COMMANDER·VIEWER·REPORTER·ADMIN.
- 유관기관(소방·경찰·군 등)은 열람자로 같은 상황도를 보는 위치(슬라이드 6 기대 효과, 대본① Q&A).

### 발표자가 말한 이유

> "법령상 현장 통합지휘와 주민대피 명령 권한은 시장·군수·구청장 한 사람에게 있습니다. 그래서 이 한 사람에게 주는 대응 제안서 하나, 표준매뉴얼 판단 항목을 따른 진화 7개·대피 7개 항목으로 출력을 바꿨습니다." (대본① 3쪽)
>
> "결정권자에게 진화 7·대피 7 항목의 제안서 하나를 주는 것이 실제 지휘 구조와 맞습니다. 유관기관은 열람자로 같은 상황도를 봅니다." (대본① Q&A)

> (정리자 해석) 2주차의 FF/RW/GO 역할 개념은 3주차에서 사라졌지만, 2주차 공무원(GO) 질의 4개(대피 우선순위·자원배분·추가 자원 필요성·행정 대응)는 3주차 S3 진화자원 투입·배분, S6 유관기관 동원·협조, E2 대피 대상·순서·시점에 흡수된 것으로 보인다. 소방요원 질의(진화 우선지역·진입 시 위험요인·주요 보호대상)는 S2·S7·S5에, 구조요원 질의(구조 우선순위·이동·이송·위험구간)는 E3·E5·E7에 대응된다. 이 대응은 문서에 명시되어 있지 않다.

## 2. 규칙 엔진과 LLM의 경계 [대본 명시]

| 구분 | 2주차 | 3주차 |
|---|---|---|
| 규칙이 판정하는 것 | 대응 단계(시행령 별표 3, 면적 10/100ha·풍속 3/11m/s·시설 20동), 행정구역 경계 통과 여부, 역할별 활성화 기관 | "근거 문서에 경계값·수치가 있는 값": 대응단계, 위험구역(P5/P8), 대피소 배정, 도달 시각, 면적. 진화 7·대피 7 항목의 발동 여부(judge_fire·judge_evac) |
| LLM이 하는 것 | ① 현장 분석: 5.2.1 수치를 검색 없이 서술(값 재계산 금지) ② 임무 부여: 역할별 질의에 RAG로 답변. "LLM은 확정된 근거 문서를 검색(RAG)하여 역할별 서술로 정리하는 역할만" | 판정 값과 상황 데이터, 검색 근거를 받아 **"진화 7·대피 7 항목의 대응을 판단해 제안 문장을 만들고"** 근거 인용. 상황 정정 입력 해석. "LLM은 그 값을 바꾸지 못하며" |
| 대본의 표현 | 「규칙이 판정, LLM은 문장만」 | 「경계값은 규칙, 판단과 문장은 근거 붙인 AI」 |

> "계획서의 「규칙이 판정, LLM은 문장만」을 「경계값은 규칙, 판단과 문장은 근거 붙인 AI」로 조정한 것입니다." (대본① 3쪽)

- 3주차는 이 경계를 비기능 요구사항 **QUR-002 판단 일관성**으로 명문화했다: "LLM이 규칙 판정값을 임의로 재계산하지 않도록 제한", "출력 구조와 S1~S7·E1~E7 항목 순서 고정".
- 3주차 출력 제약(슬라이드 104): "수치 재계산 금지, 청크 밖 내용 금지, 문장 끝 근거 번호".

> (정리자 해석) 2주차 "현장 분석"(RAG 없이 LLM이 예측 수치를 서술하는 보고서 첫 부분)은 3주차에 없다. 예측 수치는 통합 상황도(P1~P8 지도)와 위험도 패널로 바로 표출되고, LLM은 제안 문장만 쓴다. 즉 "LLM이 쓰는 글의 범위"는 좁아지고(현장 분석 삭제), "LLM이 내리는 판단의 범위"는 넓어졌다(무엇을 먼저 할지).

## 5. 생성 구조와 버전 관리 [문서 대조]

### 2주차: 보고서 1회 생성

- "보고서는 예측 산출 시점 기준 1회 생성."

- 갱신 구조는 "미정"(표 0-1 #20의 수정 전 항목에 "생성 시점·갱신 구조 미정"이 있었고, 수정 후 "1회 생성"으로 확정).

### 3주차: 항목별 파이프라인 + 버전

- ProposalOrchestrator.generate(): 규칙 판정 → 발동 항목(최대 14) → 항목마다 A1·검색·A2 → A3 충돌 검사 → A4 종합 → 인용 번호 검증 → 직전 버전 비교 → 새 버전 저장(사유: 예측 갱신 / 상황 정정).
- 제안 항목 속성: item_code(S1~E7), categories(즉시·대기·협의·요청), finding(규칙 판정 값), text(근거 번호 포함 문장), targets, conflicts(내부 검증용, 비표시), authority(직접·협의·요청), changed(변경 태그).
- 제안서는 수정하지 않고 새 버전 추가. 직전 버전 대비 바뀐 항목에 '변경' 태그 + 팝업(UC-PROP-04). 이벤트 로그에 "제안서 버전 n 생성".
- 문체: "일관된 격식체"(QUR-001). 하십시오체 명시는 없음.

> (정리자 해석) "즉시·대기·협의·요청" 분류와 "직접·협의·요청" 권한 표기는 2주차에 없던 개념이다. 2주차의 "지휘권 인계 준비 권고"가 권한 축으로 일반화된 것으로 보인다.

## 15. 열린 질문 — 분석서만으로 답할 수 없는 것 [정리자 해석]
