## 설계 원칙

이전 판에서 확정한 것 중 MVP에도 그대로 쓰는 것만 남긴다.

- **저장소**: 운영 데이터와 지도 레이어는 PostgreSQL + PostGIS. 래스터(DEM·연료 격자)와 ELMFIRE 원본 출력(도달시간 래스터 등)은 파일로 두고 DB에는 경로만. ELMFIRE 출력을 변환한 P1~P8 폴리곤은 DB(`prediction_slices`)에 저장. 근거 벡터 인덱스는 FAISS 파일
- **좌표계**: EPSG:5179(UTM-K) 하나로 저장, 지도로 보낼 때만 4326으로 변환
- **키**: 모든 테이블의 기본키는 `bigint` 대리키 `id`
- **이름**: 영어 snake_case, 테이블은 복수형, 시각은 `_at`(timestamptz)
- **상태값**: 값이 고정되면 ENUM, 계속 늘어나면 varchar
- **기록은 고치지 않고 추가**: 화선 정정·제안서 재생성은 새 행(새 버전). 이벤트 로그는 추가만
- **지역 독립**: 스키마에 특정 지역을 넣지 않음. 지역은 행정구역 코드로 데이터에서 구분

## 1. 기능 정리

### 1.1 기능 흐름

```
[입력]  ──▶  [핵심 ①] 예측  ──▶  [핵심 ②] 위험도  ──▶  [핵심 ③] 진화·대피 제안
보고·화선     P1~P8              P5 기준 R             규칙 판정 → 근거 → 제안서
                                                         │
                                         [제안 다루기] 근거 조회·질의·정정·이력
```

### 1.2 MVP 기능

| 묶음 | 기능 | F-ID | 하는 일 |
|---|---|---|---|
| **입력** | 산불 보고 | F-02, F-04 | 발화 위치·주소·일시·신고 내용·신고자 입력, 산불현황 조회 |
| | 실측 화선 보고 | F-02 | 1시간마다 화선 폴리곤(v1, v2 …), 잘못 보고하면 정정 |
| **핵심 ① 예측** | 확산 예측 실행 | F-09, F-05 | 최신 화선(화선이 없으면 발화점 = 화선 v0)과 기상으로 P1~P8 계산·지도 표시 |

### 1.3 MVP 범위 결정

| # | 항목 | 결정 | 이유 |
|---|---|---|---|
| 1 | 산불 병합(P5가 겹치면 하나로) | **제외** | 10/13 회의에서 병합 장면을 뺐고 시연은 의성 한 건. 위험도는 산불별로 계산 |
| 2 | AI 질의응답 기록 | **질문·답변만 저장** | 답변에도 근거 번호가 붙고(F-13), 근거 부족을 기록해야 함(F-32) |
| 3 | 기관별 접수 기록(접수 기관·시각·경로 목록) | **제외** (2026-10-23 팀장 결정) | F-02의 「접수 시각」은 `reported_at`으로 충족. 「접수 기관」은 판정·제안에 쓰이지 않는 표시용이라 MVP에서 뺌. 프로토타입 v4에는 줄 단위 입력·표시가 있었음 |
| 4 | 정정의 진화자원 투입 수("헬기 2대 추가") | **포함** (2026-10-23 팀장 결정) → **2026-11-06 바꿈** | 헬기·차량은 관리자가 자원을 산불에 **연결**한다(`resources.deployed_incident_id`, F-31). S3가 「무엇이 어느 기지에서 투입됐나」를 알려면 자원 단위 연결이 필요하기 때문. 산불별 투입 수(`situation.deployed`)는 **인력과 `resources`에 없는 자원(군·경찰 헬기 등)**만 맡는다 |
| 5 | 진화예상시간 | **제외** (2026-10-27 팀장 결정) | 매뉴얼 p.73 판단 기준표 4요소 중 하나지만, 시스템이 구할 수 없고 현장 사람이 판단해 알려 줘야 하는 값이다. 매뉴얼의 단계 정의는 피해면적·시설피해 중심이라 나머지 3요소(피해면적·평균풍속·시설피해)로 판정한다. 입력 칸·정정 항목·`incidents.situation`에 두지 않는다 |
| 6 | 공식 대응단계(산림청장 발령) | **제외** (2026-11-02) | 산림청장이 실제로 발령한 단계는 시스템이 알 수 없다고 가정한다. 산불 보고·상황 정정에서 단계를 입력받지 않고, 현재 단계는 **화선을 보고·정정할 때마다** 규칙 엔진이 그 화선으로 매뉴얼 p.73 판단기준을 적용해 판정하고 `incidents.current_stage`에 넣는다. 제안서는 생성 때 그 값을 `proposals.judged_stage`로 복사하고, 5시간 뒤 단계는 P5 기준(`predicted_stage`) |
| 7 | 위기경보(관심·주의·경계·심각) | **제외** (2026-11-06) | 산림청이 발령하는 값이고 기준이 산불위험지수·회의 판단이라 규칙 엔진이 판정할 수 없다(매뉴얼 p.50). 판정·제안 어디에도 쓰지 않아 산불 보고 입력·상황 정정 항목·`incidents` 칸에서 뺀다. 매뉴얼의 「경계 → 이송 준비, 심각 → 이송」은 구역(잠재 위험구역 / 위험구역)으로 대신한다(규칙 엔진 E3) |

## 2. 테이블 정의

묶음 하나씩 정의한다. 표기: `NN` = NOT NULL, `PK`·`FK`·`UK` = 기본키·외래키·유일. 다른 묶음 테이블을 가리키는 FK는 그 묶음에서 테이블이 정해질 때 연결된다.

### 2.1 계정

#### `users` — 계정

사용자 한 명 = 1행. 전산 관리자가 발급하고 회원가입은 없다.

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | bigint | PK | |
| `login_id` | varchar(50) | NN, UK(대소문자 무시) | 로그인 아이디. 예: `cmd01` |
| `password_hash` | text | NN | 비밀번호 해시 |
| `name` | varchar(50) | NN | 이름 |
| `organization` | varchar(100) | NN | 소속 기관 |
| `role` | `user_role` ENUM | NN | `COMMANDER`(통합지휘권자)·`VIEWER`(열람자)·`REPORTER`(상황 보고자)·`ADMIN`(전산 관리자) |
| `admin_area_id` | bigint | FK → `admin_areas` | 관할 시군구. 전산 관리자만 NULL(전체) |
| `failed_login_count` | smallint | NN, 기본 0 | 연속 로그인 실패 횟수. **5 이상이면 잠김** |
| `created_at` | timestamptz | NN, 기본 now() | 발급 시각 |
| `updated_at` | timestamptz | NN, 기본 now() | 마지막 변경 시각 |
| `deleted_at` | timestamptz | | 회수·삭제 시각. **NULL이면 사용 중** |

- 로그인 거부: `deleted_at`이 있거나 `failed_login_count >= 5`
- 잠금 해제는 전산 관리자가 `failed_login_count = 0`으로
- 회수·삭제는 행을 지우지 않고 `deleted_at`만 기록(이벤트 로그·산불이 계정을 가리킴)
- 관할의 마지막 통합지휘권자는 회수·권한 변경 불가
- API 요청마다 `users` 행을 읽어 권한·회수 여부를 확인(JWT만 쓰고 세션 테이블은 두지 않음)

#### `event_logs` — 이벤트 로그

**누가, 언제, 어느 산불에서, 무엇을 했는지** 1건 = 1행. **추가만** 한다(수정·삭제 권한 회수). 화면에 보이는 구분·문장은 저장하지 않고 조회할 때 `action`·`details`로 만든다.

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | bigint | PK | |
| `created_at` | timestamptz | NN, 기본 now() | 언제 |
| `user_id` | bigint | FK → `users` | 누가. 시스템 이벤트는 NULL |
| `incident_id` | bigint | FK → `incidents` | 어느 산불. 로그인·계정 관리는 NULL |
| `action` | varchar(50) | NN | 무엇을. 예: `LOGIN_FAILED`, `PERIMETER_REPORTED`, `PROPOSAL_CREATED`, `ITEM_NO_EVIDENCE` |
| `details` | jsonb | | 세부 사실(대상 id, 버전, 변경 전후 값). **개인정보는 넣지 않음** |

### 2.2 산불·보고

상황 보고자는 지도에 **발화 지점을 점 하나로 찍고**, 이후 점을 여러 개 찍어 **산불 범위를 폴리곤으로** 그린다. 점은 `incidents`, 폴리곤은 `fire_perimeters`에 저장한다. 첫 보고에서 점만 찍고 폴리곤은 나중에 그려도 되고(초기대응), 둘을 같이 보고해도 된다.

발화점은 `fire_perimeters`에도 **화선 v0**(점)으로 함께 넣는다. 그러면 예측의 시작 형상이 항상 `fire_perimeters`의 한 행이 되어, 「발화점이면 따로 처리」하는 규칙(예측 시작점·0시·제안서 버전 앞 번호)이 필요 없다.

#### `incidents` — 산불 사건

**어떤 테이블**: 산불 하나 = 1행. 보고 내용·진행상태·**현재 상황**을 담는다. 산불명은 따로 입력받지 않고 발화 지점의 행정구역과 날짜로 만들어 보여 준다(예: 「의성군 안평면 산불 (2025-03-22)」). 주소는 상황 보고자가 입력한다.

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | bigint | PK | |
| `ignition_point` | geometry(Point, 5179) | NN | 발화 지점. 보고자가 지도에 찍음 |
| `address` | varchar(200) | NN | 발생 장소 주소. 보고자가 입력(임야는 「안평면 괴산리 산61 일원」처럼) |
| `admin_area_id` | bigint | NN, FK → `admin_areas` | 발화 지점이 속한 **읍면동**(저장 시 자동 계산). 상위 시군구가 관할 |
| `started_at` | timestamptz | | 발생 일시. 모를 수 있어 NULL 허용 |
| `reported_at` | timestamptz | NN | 신고 접수 일시 |
| `report_text` | text | | 신고 내용 |
| `reporter_org` | varchar(100) | | 신고 기관명. 관계기관이 신고한 경우만 입력, 주민 신고면 NULL(규정 제6조①1) |
| `reporter_name` | varchar(50) | NN | 신고자 성명(규정 제6조제1항제1호). 모르면 「미상」 입력 |
| `reporter_phone` | varchar(20) | NN | 신고자 연락처(규정 제6조제1항제1호). 모르면 「미상」 입력 |
| `status` | `incident_status` ENUM | NN, 기본 `IN_PROGRESS` | `IN_PROGRESS`(진행 중)·`ENDED`(종료). 화선이 아직 없는지는 `fire_perimeters`에 `version_no ≥ 1`인 행이 있는지로 판단 |
| `current_stage` | `response_stage` ENUM | NN, 기본 `INITIAL` | **현재 대응단계**: `INITIAL`(초기대응)·`STAGE1`·`STAGE2`(확산대응 1·2단계). 사람이 입력하지 않고, **화선을 보고·정정할 때마다** 규칙 엔진이 그 화선의 면적·그 시각 풍속·시설피해 우려 동수(P5 안 주택 + 국가유산, 시행령 [별표 3] 비고 4)로 판정해 UPDATE(매뉴얼 p.73). 산불 보고 때는 v0(발화점, 면적 0)으로 판정. 산림청장 공식 발령은 두지 않음(1.3의 6번) |
| `situation` | jsonb | NN, 기본 `{}` | **현재 상황**(아래). 상황 정정으로 바뀜 |
| `reported_by` | bigint | NN, FK → `users` | 이 산불을 시스템에 **처음 등록한 상황 보고자 계정**. 119에 신고한 사람(`reporter_name`)과 다름 |
| `created_at` | timestamptz | NN, 기본 now() | 등록 시각 |
| `ended_at` | timestamptz | | 종료 시각 |
| `ended_by` | bigint | FK → `users` | 종료 처리한 통합지휘권자 계정. 산불현황에 「종료 18:00 · cmd01」로 표시 |

`situation` 형태 — 마을 키는 `villages.id`:

```json
{
  "villages": { "1024": { "evacuated": true, "evac_order": true } },
  "deployed": {
    "helicopter": { "total": 2, "military": 2 },
    "vehicle":    { "total": 2, "other": 2 },
    "crew":       { "total": 357, "special_crew": 187, "forest_officials": 113, "fire": 57, "military": 0, "police": 0, "other": 0 }
  },
  "disaster_sms_sent": true
}
```

`deployed` — 이 산불에 **투입된** 진화자원 수. 산림청 「산불 상황 보고」 양식(의성산불백서 부록 3)의 「현재 진화자원」 칸을 그대로 따른다. **11/6부터 헬기·차량 중 `resources`에 있는 것은 자원 연결(`resources.deployed_incident_id`)로 세고, 여기에는 넣지 않는다** — 여기는 인력과 `resources`에 없는 자원(군·경찰 헬기 등)만. 보고 양식의 합계 = 자원 연결 수 + 이 값

| 키 | 보고 양식 | 구분 |
|---|---|---|
| `helicopter` | 산불진화 헬기 | `forest`(산림청) · `local`(지자체) · `fire`(소방) · `military`(군) |
| `vehicle` | 장비 | `forest_vehicle`(산불진화·지휘차) · `fire_truck`(소방차) · `other`(기타) |
| `crew` | 인력 | `special_crew`(산불특수진화대 등) · `forest_officials`(산림공무원) · `fire`(소방) · `military`(군) · `police`(경찰) · `other`(기타) |

- `total`은 꼭 있고, 구분 값은 아는 것만 넣는다. 「헬기 2대 추가」처럼 구분을 모르는 정정은 `total`만 바꾼다
- 보유·대기는 여기가 아니라 `resources`에 있다(2.6). 인력은 보유를 관리하지 않으므로 투입 수만 있다

**데이터가 쌓이는 방식**

- 새 산불 보고 → 1행 INSERT(`IN_PROGRESS`). 같은 트랜잭션에서 발화점을 `fire_perimeters` v0으로 INSERT
- 상황 정정을 확인하면 → `situation` UPDATE(정정 이력은 `situation_corrections`에 쌓임)
- 종료 → `status = ENDED`, `ended_at`·`ended_by`
- 삭제하지 않는다. 산불 하나당 행은 계속 1개

**기능에서 쓰이는 곳**

| 기능 | 사용 |
|---|---|
| F-02 산불 보고 | INSERT |
| F-04 산불현황 | 주소·발생·신고·신고자·진행상태·현재 대응단계(`current_stage`) 읽기 |
| F-05 지도 | 발화 지점 표시 |
| F-09 예측 | 직접 쓰지 않음. 발화점은 `fire_perimeters` v0으로 시작 |
| F-11·F-15 제안 | `situation`을 규칙 판정 입력으로. 대응단계는 저장하지 않고 규칙 엔진이 판정(1.3의 6번) |
| F-30 정정 | `situation` UPDATE |
| F-03 종료 | `status`. 이후 보고·예측·정정 차단의 기준 |

#### `fire_perimeters` — 실측 화선

**어떤 테이블**: 상황 보고자가 점을 이어 그린 **산불 범위 1건 = 1행**. 찍은 점들은 폴리곤 하나로 저장한다. **v0은 발화점(점)**으로, 산불 보고 때 자동으로 넣는다.

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | bigint | PK | |
| `incident_id` | bigint | NN, FK → `incidents` | |
| `version_no` | int | NN | 화선 버전. **0 = 발화점**, 1, 2 … = 실측 화선 |
| `geom` | geometry(Geometry, 5179) | NN | v0은 Point(발화점), v1 이상은 MultiPolygon(실측 연소 범위). 이 두 형태만 허용(CHECK) |
| `observed_at` | timestamptz | NN | 관측 시각. v0은 `incidents.started_at`, NULL이면 `reported_at` |
| `reported_by` | bigint | NN, FK → `users` | 이 화선을 그린 상황 보고자 계정(v0은 산불을 등록한 계정). 산불현황 화선 줄에 「11:55 rep01」로 표시 |
| `created_at` | timestamptz | NN, 기본 now() | 등록 시각 |
| `corrected_at` | timestamptz | | 잘못 그려서 **정정된 시각**. NULL이면 유효, 값이 있으면 「정정됨」 |

- 유일: `(incident_id, version_no)` — 정정해도 번호는 새로 매기므로 같은 번호는 하나뿐
- 현재 화선 = `corrected_at IS NULL`인 것 중 `version_no`가 가장 큰 행. 실측 화선이 아직 없으면 v0(발화점)
- 면적(ha)은 저장하지 않고 `ST_Area`로 계산(v0은 0)
- v0은 발화 정보라서 화선 정정 대상이 아니다. 발화점은 `incidents.ignition_point`와 v0 두 곳에 있지만 산불 보고 때 함께 넣고 MVP에는 발화 정보 수정이 없어 어긋나지 않는다

**데이터가 쌓이는 방식**

- 산불 보고 → v0(발화점) 1행 INSERT
- 새 화선 보고 → 다음 번호로 1행 INSERT. 1시간마다 보고하므로 8시간이면 산불 하나에 v0 포함 약 9행. 같은 트랜잭션에서 규칙 엔진이 새 화선으로 단계를 판정해 `incidents.current_stage` UPDATE
- 정정 → 기존 행에 `corrected_at` 기록 + 고친 화선을 **다음 번호로** INSERT. 원래 행은 남김(아래 「화선 정정」)

**기능에서 쓰이는 곳**

| 기능 | 사용 |
|---|---|
| F-02 화선 보고·정정(UC-REPORT-01 대안 흐름 A2) | INSERT, 정정 시 `corrected_at`. 보고·정정마다 `incidents.current_stage` 다시 판정 |
| F-05 지도 | 최신 유효 화선·이전 버전 표시(v0은 발화점 표시) |
| F-04 산불현황 | 최신 화선 버전·면적(v0만 있으면 「화선 없음」) |
| F-09 예측 | 현재 화선(없으면 v0 발화점)을 시작점으로 |
| 「재예측 필요」 | 최신 화선 버전 > 마지막 예측의 기준 화선 버전이면 표시 |
| F-11 제안서 버전 | `v(화선 버전).(순번)`의 앞 번호. 발화점에서 예측하면 v0.1 |

#### 화선 정정 — 무엇이 일어나나

상황 보고자가 **잘못 그린 화선**을 다시 그려 제출하는 것(UC-REPORT-01 대안 흐름 A2, 프로토타입 27쪽 ⑤). AI 상황 정정(F-30)과는 다른 기능이다.

예: 12:55에 v2를 잘못 그려 냈고, 13:05에 정정

| id | version_no | observed_at | corrected_at | 상태 |
|---|---|---|---|---|
| 10 | 1 | 11:55 | | 유효 |
| 11 | 2 | 12:55 | **13:05** | 정정됨 |
| 12 | **3** | 13:05 | | **유효(현재 화선)** — 산불현황에 「v3 (v2 정정)」 |

| 순서 | 일어나는 일 | 테이블 |
|---|---|---|
| 1 | 산불이 종료되지 않았는지 확인, 정정 대상은 **현재 화선(v2)** 하나뿐 | `incidents`, `fire_perimeters` |
| 2 | v2에 `corrected_at = 13:05` | `fire_perimeters` UPDATE |
| 3 | 고친 화선을 **v3**로 추가하고, v3로 현재 대응단계를 다시 판정 | `fire_perimeters` INSERT, `incidents.current_stage` UPDATE |
| 4 | 「화선 정정 v2 → v3」 기록 | `event_logs` (`PERIMETER_CORRECTED`) |
| 5 | v2로 이미 예측했다면 통합지휘권자 화면에 **「재예측 필요」** 표시. 예측은 자동으로 돌지 않음 | 조회만 |

**바뀌지 않는 것**: v2로 만든 기존 예측·위험도·제안서는 그대로 남는다. 이력에는 「기준 화선 v2(정정됨)」로 보인다. 통합지휘권자가 「다시 예측」을 누르면 v3 기준으로 새로 계산되고 제안서는 v3.1이 된다.

### 2.3 예측

통합지휘권자가 「확산 예측 실행 / 다시 예측」을 누르면, 그 시점의 **현재 화선**(실측 화선이 없으면 v0 발화점)에서 1시간 간격 누적 확산 범위 P1~P8을 계산한다. 실행 1회는 `predictions`, P1~P8은 `prediction_slices`에 저장한다. 지형·연료 격자는 파일로 두고 DB에 넣지 않는다. 예측 모델(ELMFIRE 또는 AI, 10/27 결정)이 바뀌어도 출력은 P1~P8 폴리곤이라 이 구조는 그대로다.

#### `predictions` — 확산 예측

**어떤 테이블**: **성공한 예측 1회 = 1행**. 어떤 형상에서, 몇 시를 0시로, 어떤 기상으로 계산했는지를 담는다.

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | bigint | PK | |
| `incident_id` | bigint | NN, FK → `incidents` | |
| `perimeter_id` | bigint | NN, FK → `fire_perimeters` | 시작 형상인 화선. v0이면 발화점에서 시작 |
| `base_at` | timestamptz | NN | **P1~P8의 0시**. Pn의 시각 = `base_at` + n시간(아래) |
| `weather` | jsonb | NN | 예측에 넣은 시간별 기상(아래) |
| `requested_by` | bigint | NN, FK → `users` | 실행한 통합지휘권자 계정 |
| `created_at` | timestamptz | NN, 기본 now() | 저장 시각 |

- 현재 예측 = 그 산불에서 `id`가 가장 큰 행
- 예측 자체에는 버전 번호를 두지 않는다. 순서는 `id`, 기준 화선은 `perimeter_id`로 알 수 있고, 화면에 보이는 버전(`v화선.순번`)은 제안서 버전이다
- 진행 상태(`RUNNING`·`FAILED`)와 끝난 시각은 두지 않는다. 실패하면 행을 남기지 않고 `event_logs`에 `PREDICTION_FAILED`로 기록한다

**`base_at` — P1~P8의 0시**

예측 모델은 「시작 형상에서 n시간 뒤」만 계산한다. 이를 「몇 시」로 바꾸는 기준이 `base_at`이다. 예측을 저장할 때 한 번 정한다.

`base_at` = 시작 형상(`perimeter_id`)의 `observed_at`. 발화점(v0)이면 발생 일시, 없으면 접수 일시가 이미 `observed_at`에 들어 있다.

- 「다시 예측」을 **누른 시각이 아니다**. 12:55 관측 화선으로 13:20에 예측해도 0시는 12:55다(누른 시각을 쓰면 그 사이에 번진 만큼이 빠짐)
- 쓰는 곳: 지도 시간 재생(「P1 = 13:55」), 마을 도달 시각(E2 대피 순서), 야간 도달 판단(S4·E2, 일몰 시각과 비교), 기상 시간 맞추기

**`weather` 형태** — 출처는 [`데이터-자원.md`](데이터-자원.md) D-25·D-26

```json
{
  "source": "KMA_FORECAST",
  "issued_at": "2026-10-26T11:00:00+09:00",
  "location": { "nx": 88, "ny": 102 },
  "hours": [
    { "at": "2026-10-26T12:00:00+09:00", "wind_dir": 270, "wind_speed": 5.1, "temp": 21.8, "humidity": 23, "precip": 0.0 }
  ]
}
```

| 키 | 설명 |
|---|---|
| `source` | `KMA_FORECAST`(단기예보, 운영) · `AWS_OBS`(AWS 관측, 시연·평가). 시연은 과거 날짜라 예보를 받을 수 없음 |
| `issued_at` | 예보 발표 시각. 관측이면 `null` |
| `location` | 예보면 격자 `{nx, ny}`, 관측이면 관측소 `{stn}`. 정하는 방법은 아래 |
| `hours[]` | `base_at`을 내림한 정시부터 8시간 뒤까지 1시간 간격 **9개**(예보·관측이 정시 단위라서). 예: `base_at` 12:55 → 12:00~20:00 |
| `wind_dir` · `wind_speed` · `temp` · `humidity` · `precip` | 풍향(°, 불어오는 방향) · 풍속(m/s) · 기온(℃) · 상대습도(%) · 1시간 강수(mm). 단기예보의 강수 문자열(「강수없음」 등)은 숫자로 바꿔 저장 |

- 위험도·규칙 판정(S1 풍속, S4)·제안이 예측과 **같은 기상**을 쓰도록 예측 행에 함께 둔다. 기상 캐시 테이블은 두지 않는다
- 시정·특보·기압·지면온도는 예측 입력이 아니어서 넣지 않는다(위험도 묶음에서 다룸)

**`location` 정하는 방법** — 예측할 때마다 그 산불의 시작 형상에서 자동으로 정한다

1. 기준점: 시작 형상이 점(v0 발화점)이면 그 점, 폴리곤이면 `ST_PointOnSurface`(항상 폴리곤 안의 점. 무게중심은 휜 화선에서 불 바깥에 찍힐 수 있음)
2. 기준점을 EPSG:4326 위경도로 변환
3. 지점 결정
   - 예보: 기상청 단기예보 API 문서의 격자 변환 공식으로 `{nx, ny}`(5 km 격자). 예: 의성 발화점 부근(36.40, 128.55) → (88, 102). 발표 시각은 `hours` 범위를 모두 포함하는 가장 최근 발표
   - 관측: 그 시각에 운영 중인 AWS 관측소 중 기준점에서 가장 가까운 곳 `{stn}`. 값이 비면 2·3순위 관측소로 채움

- 산불마다, 예측마다 따로 정한다. 산불 2개면 각자 위치의 기상이 들어가고, 화선이 커져 기준점이 옮겨지면 다음 예측의 격자가 바뀔 수 있다

**한계 — 한 지점 기상을 전체에 적용**

기준점 한 곳의 기상을 8시간 동안 예측 범위 전체에 똑같이 쓴다(확산 코드도 바람이 공간적으로 균일하다고 가정). 2025-03-22 의성 주변 AWS 12곳(30 km 이내)을 비교하면 기온(약 3 ℃ 차)·습도는 거의 같지만 **풍속(2.9~8.6 m/s)·풍향(최대 100° 이상 차)은 지점마다 크게 달랐다**. 지형에 따른 바람 차이를 반영하려면 별도 바람 모델(WindNinja 등)이 필요해 MVP에서 제외하고, 예측 오차 원인의 하나로 기록한다.

#### `prediction_slices` — 시간별 확산 범위 P1~P8

**어떤 테이블**: 예측 1회의 **1시간 간격 누적 확산 범위 1개 = 1행**. 예측 1회에 8행.

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | bigint | PK | |
| `prediction_id` | bigint | NN, FK → `predictions` | |
| `hour` | smallint | NN, 1~8 | P1~P8. 이 범위의 시각 = `base_at` + `hour`시간 |
| `geom` | geometry(MultiPolygon, 5179) | NN | 누적 확산 범위. P(n) ⊇ P(n−1)을 검증한 뒤 저장 |

- 유일: `(prediction_id, hour)`
- 위험구역 = P5(`hour = 5`), 잠재 위험구역 = P8(`hour = 8`)
- 마을 도달 시각 = 마을과 겹치는 `hour`의 최솟값 → `base_at` + 그 시간
- 면적(ha)은 저장하지 않고 `ST_Area`로 계산(대응단계 기준 10·100 ha 판정에 사용)
- 행으로 나눈 이유: 위처럼 시간별로 공간 질의를 하기 위함

**데이터가 쌓이는 방식**

- 예측 성공 → `predictions` 1행 + `prediction_slices` 8행을 **추가만** 한다. 고치거나 지우지 않는다
- 예측 → P1~P8 → 위험도 → 제안서 계산을 모두 마친 뒤 **한 트랜잭션**으로 저장한다(계산하는 몇 분 동안 트랜잭션을 열어 두지 않음). 중간에 실패하면 아무것도 남지 않아 직전 예측·제안서가 그대로 현재가 된다(UC-PRED-01 예외 흐름 E2·E3)
- 중복 실행은 버튼 비활성화와 서버의 산불별 잠금(PostgreSQL advisory lock)으로 막는다. 실행 중에 다시 요청하면 「이미 실행 중」을 돌려준다(E1)
- 종료된 산불(`incidents.status = ENDED`)은 예측하지 않는다
- 1시간마다 다시 예측하면 8시간에 약 8회 → `predictions` 약 8행, `prediction_slices` 약 64행

**기능에서 쓰이는 곳**

| 기능 | 사용 |
|---|---|
| F-09 예측 실행 | INSERT |
| F-05 지도 | 현재 예측의 P1~P8 시간 재생(`base_at` + `hour`), P5·P8 강조 |
| F-04 산불현황 | 5h·8h 예측 면적, 기준 화선, 예측 시각 |
| F-10 위험도 | 현재 예측의 P5와 `weather` |
| F-11·F-15~F-28 제안 | 규칙 판정 입력: P5·P8 안의 마을·시설, 도달 시각, 면적, 풍속 |
| F-14 이력 | 제안서 버전이 어느 예측(기준 화선)에서 나왔는지 |
| 「재예측 필요」 | 최신 유효 화선 버전 > 현재 예측의 기준 화선 버전이면 표시 |

#### 예측이 쌓이는 예 — 화선 v1·v2·v3

예측은 누른 시점의 최신 유효 화선으로만 돈다. 지난 화선을 골라 예측하지 않는다.

| 시각 | 일어난 일 | `predictions` | 기준 화선 | `base_at` | 제안서 |
|---|---|---|---|---|---|
| 11:55 | 화선 v1 보고 | | | | |
| 12:05 | 예측 | id 1 | v1 | 11:55 | v1.1 |
| 12:55 | 화선 v2 보고 → 「재예측 필요」 | | | | |
| 13:05 | 다시 예측 | id 2 | v2 | 12:55 | v2.1 |
| 13:30 | 기상만 바뀌어 같은 v2로 다시 예측(UC-PRED-01 A2) | id 3 | v2 | 12:55 | v2.2 |
| 13:55 | 화선 v3 보고 → 「재예측 필요」 | | | | |
| 14:05 | 다시 예측 | id 4 | v3 | 13:55 | v3.1 |

- 현재 예측은 id 4. 지도·위험도·규칙 판정이 모두 이것을 쓴다
- 같은 화선의 id 2·3은 `base_at`이 같고 `weather`가 다르다. 둘 다 남는다
- v2를 정정해 v3이 생겨도 v2 기준 예측(id 2·3)은 그대로 남고, 이력에는 「기준 화선 v2(정정됨)」로 보인다

### 2.4 제안

예측이 끝나면 규칙 엔진이 판정하고, 근거를 검색하고, LLM이 진화 S1~S7·대피 E1~E7 항목의 제안 문장을 써서 **제안서 새 버전**으로 저장한다. 제안서는 예측이 있어야만 생긴다. 상황 정정(F-30)은 예측을 다시 돌리지 않고 같은 예측으로 제안서만 새 버전을 만든다.

| 테이블 | 1행 = | 내용 |
|---|---|---|
| `proposals` | 제안서 버전 1개 | 버전 번호, 기준 예측, 계기, 공식·판정(현재·예측) 대응단계 |
| `proposal_items` | 발동한 항목 1개(제안서당 최대 14) | 진화·대피, 항목 코드, 구분, 제안 문장, 상세(판정 이유·대상) |
| `citations` | 문장 속 근거 번호 [k] 1개 | 어느 근거 청크인지 |
| `evidence_chunks` | 근거 청크 1개 | 문서·쪽·항목·본문 |

#### `proposals` — 제안서

**어떤 테이블**: **제안서 버전 1개 = 1행**. 버전은 `v(화선 버전).(순번)`이다. 화선 v1 기준 첫 제안 v1.1 → 상황 정정 v1.2 → 화선 v2로 다시 예측 v2.1. 발화점(화선 v0)에서 예측했으면 v0.1.

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | bigint | PK | |
| `incident_id` | bigint | NN, FK → `incidents` | |
| `prediction_id` | bigint | NN, FK → `predictions` | 기준 예측. 상황 정정 버전도 같은 예측을 가리킨다 |
| `perimeter_version` | smallint | NN | 버전 앞 번호 = 기준 예측의 시작 형상 `version_no`(발화점이면 0) |
| `seq` | smallint | NN | 버전 뒷 번호. 같은 `perimeter_version` 안에서 1, 2 … |
| `trigger` | `proposal_trigger` ENUM | NN | 계기: `PREDICTION`(예측 갱신) · `CORRECTION`(상황 정정) |
| `correction_id` | bigint | FK → `situation_corrections` | 정정 버전일 때만 값이 있음 |
| `judged_stage` | `response_stage` ENUM | NN | **현재 기준** 대응단계. 생성 당시 `incidents.current_stage`를 복사한다(화선이 바뀌면 그 값이 바뀌므로 그때 값을 남긴다) |
| `predicted_stage` | `response_stage` ENUM | NN | **예측 기준** 판정 단계. 같은 기준을 P5 면적·0~5시간 평균풍속·P5 안 시설(주택 + 국가유산 동수, `current_stage`와 같은 값)에 적용 |
| `created_at` | timestamptz | NN, 기본 now() | 생성 시각 |

- 유일: `(incident_id, perimeter_version, seq)`
- 현재 제안서 = 그 산불에서 `id`가 가장 큰 행
- `perimeter_version`은 `prediction_id → perimeter_id → version_no`로도 구할 수 있지만, 같은 버전 번호가 두 번 생기지 않도록 유일 조건에 쓰려고 저장한다
- 공식 대응단계(산림청장 발령)는 두지 않는다(1.3의 6번)
- 격상 관련 표시는 저장하지 않고 두 단계를 비교해 정한다: `predicted_stage` > `judged_stage` → **격상 대비 안내**(5시간 안에 상위 단계 기준에 닿을 것으로 예측)
- 판정 요소는 매뉴얼 p.73 판단 기준표 중 3개다(진화예상시간은 MVP 제외, 1.3의 5번). 요소를 합치는 방법은 매뉴얼에 없어 「하나라도 상위 기준이면 상위 단계」로 정한다

| 요소 | 초기대응 | 확산대응 1단계 | 확산대응 2단계 |
|---|---|---|---|
| 피해면적(산불영향구역) | 10 ha 미만 | 10~100 ha 미만 | 100 ha 이상 |
| 평균풍속 | 3 m/s 미만 | 3~11 m/s 미만 | 11 m/s 이상 |
| 시설피해 | 우려 없음 | 주택 등 주요시설 20동 미만 피해 우려 | 20동 이상 피해 우려 |

- `judged_stage`는 화선을 보고할 때 판정한 값(그 시각 풍속), `predicted_stage`는 예측의 P5와 0~5시간 평균풍속으로 판정한 값이다
- 누가 만들었는지는 예측 버전이면 `predictions.requested_by`, 정정 버전이면 정정 기록의 사용자로 알 수 있다

#### `proposal_items` — 제안 항목

**어떤 테이블**: 제안서 하나에서 **발동한 항목 1개 = 1행**. 발동하지 않은 항목과 근거를 찾지 못한 항목은 행을 만들지 않는다.

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | bigint | PK | |
| `proposal_id` | bigint | NN, FK → `proposals` | |
| `axis` | `item_axis` ENUM | NN | `SUPPRESSION`(진화) · `EVACUATION`(대피). 진화·대피 탭 구분 |
| `item_code` | varchar(10) | NN | 항목 코드. 예: `S1`. **ENUM이 아닌 문자열**이라 항목이 늘거나 줄어도 DB는 그대로다 |
| `categories` | `item_category[]` | NN | 구분(하나 이상): `IMMEDIATE`(즉시) · `STANDBY`(대기) · `CONSULT`(협의) · `REQUEST`(요청). 예: S5 시설 보호는 소방차 배치 「즉시」 + 한전 전류 차단 「요청」 |
| `text` | text | NN | 제안 문장. 문장 끝에 근거 번호 [k]. 근거 없는 수량은 「근거가 부족하여 표시하지 않았습니다」로 둔다 |
| `detail` | jsonb | NN, 기본 `{}` | **규칙 엔진이 이 항목에 대해 판정한 내용**(아래). LLM에 넘긴 판정 값이 그대로 남는다 |

`detail` — 규칙 엔진이 판정한 내용

- 규칙 엔진이 항목마다 판정한 값은 LLM에 넘겨 제안 문장(`text`)을 쓰게 하고, 같은 값을 `detail`에 저장한다. 판정 값은 규칙 엔진이 정하고 LLM은 바꾸지 못하므로, 규칙 엔진의 결과(`detail`)와 LLM의 문장(`text`)을 나눠 둔다
- 항목마다 판정 값의 모양이 다르고 규칙 엔진을 만들면서 계속 바뀌므로 jsonb로 둔다. **구체적인 키는 규칙 엔진을 설계할 때 정한다**
- 지금 화면에서 쓰는 것은 두 가지다: 판정 이유 문장(펼침 상세), 대상 마을·시설 id(지도 강조)

```json
{
  "finding": "현재 피해면적 8 ha / P5 233 ha → 확산대응 2단계 기준",
  "targets": { "villages": [1024], "facilities": [55] }
}
```

- 유일: `(proposal_id, item_code)`
- 컬럼으로 둔 것(`axis`·`item_code`·`categories`·`text`)은 DB가 쓰는 값이다: 진화·대피 탭, 유일 조건, 구분 필터·건수, 직전 버전 비교, 근거 연결. 화면에 보여 주기만 하는 값은 `detail`에 둔다
- **항목 목록**(항목 코드·이름·순서)은 DB에 두지 않고 **코드 상수**로 둔다. 항목을 추가하려면 어차피 규칙 엔진 판정 로직과 LLM 프롬프트를 함께 바꿔야 하기 때문이다. 없어진 항목도 상수에서 지우지 않고 「사용 안 함」으로 남겨 지난 제안서의 이름이 그대로 나오게 한다
- 권한(직접·협의·요청)은 저장하지 않는다. 항목마다 고정값이고, 구분에 이미 협의·요청이 있어 화면에도 보여 주지 않는다
- 근거를 찾지 못해 뺀 항목은 `event_logs`에 `ITEM_NO_EVIDENCE`(제안서 id·항목 코드)로 남긴다
- 바뀐 항목이 없어도 새 버전에는 발동한 항목을 모두 새로 저장한다. 버전 하나만 읽어도 제안서 전체가 보이게 하기 위함이다
- 「변경」 태그(F-14)는 저장하지 않는다. 직전 버전과 `item_code`끼리 `categories`·`text`를 비교해 계산한다. 새로 생긴 항목·빠진 항목도 같은 비교로 알 수 있다

#### `citations` — 근거 인용

**어떤 테이블**: 제안 문장이나 AI 답변 속 **근거 번호 [k] 1개 = 1행**.

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | bigint | PK | |
| `item_id` | bigint | FK → `proposal_items` | 제안 문장의 근거 |
| `message_id` | bigint | FK → `qa_messages` | AI 답변의 근거(F-29) |
| `k` | smallint | NN | 문장 속 번호 |
| `chunk_id` | bigint | NN, FK → `evidence_chunks` | |

- `item_id`와 `message_id` 중 **하나만** 값이 있다(CHECK)
- 유일: `(item_id, k)`, `(message_id, k)`

#### `evidence_chunks` — 근거 청크

**어떤 테이블**: 매뉴얼·법령·규정을 잘라 둔 **청크 1개 = 1행**. 서비스가 만드는 것이 아니라 RAG 준비 작업(청킹·임베딩)의 결과를 넣는다. LLM은 GPU 서버에서 돌지만, 근거 검색과 근거 조회에 쓰는 청크는 이 테이블에 둔다.

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | bigint | PK | |
| `code` | varchar(50) | NN, UK | 청크 이름. 예: `SM-p073-01`. **한 번 정하면 바꾸지 않는다** |
| `doc_name` | varchar(200) | NN | 예: 「산불 재난」 위기관리 표준매뉴얼(2026.6) |
| `page` | int | | 쪽. 법령처럼 쪽이 없으면 NULL |
| `section` | varchar(200) | | 항목·조항. 예: 대응단계 판단기준 |
| `text` | text | NN | 본문(약 400자). LLM 입력이자 근거 조회 화면에 그대로 표시 |
| `item_codes` | varchar(10)[] | | 연결 항목(예: `S1`). 검색할 때 항목으로 거르는 데 쓴다 |
| `retired_at` | timestamptz | | 다시 청킹해서 더 쓰지 않게 된 시각. **NULL이면 검색 대상** |

- 다시 청킹하면 새 `code`로 행을 추가하고 옛 행은 `retired_at`만 기록한다. 지난 제안서의 근거가 계속 열려야 하기 때문이다
- 벡터(임베딩)는 **미정**이다. pgvector로 정하면 이 테이블에 `embedding` 컬럼 하나를 더하고, FAISS로 정하면 DB 밖 파일에 두고 FAISS 번호 ↔ `code` 대응만 둔다(근거 저장소 결정, 김지오)
- 근거 요약은 두지 않는다. 근거 조회 화면에 본문을 그대로 보여 준다

**데이터가 쌓이는 방식**

- 예측 → P1~P8 → (위험도) → 제안서 계산을 모두 마친 뒤, `proposals` 1행 + `proposal_items` 최대 14행 + `citations`를 예측과 **한 트랜잭션**으로 저장한다. 실패하면 아무것도 남지 않는다(UC-PRED-01 E3)
- 상황 정정 확인 → 같은 `prediction_id`로 `proposals` 1행(`CORRECTION`, `seq` + 1)과 항목·인용을 새로 저장
- 저장하면 `event_logs`에 `PROPOSAL_CREATED`(버전·계기·변경 항목 수)
- 고치거나 지우지 않는다. 종료된 산불은 새 버전을 만들지 않고, 마지막 버전을 조회만 한다
- `evidence_chunks`는 RAG 준비 작업에서 한 번 넣고, 다시 청킹할 때만 추가한다

**기능에서 쓰이는 곳**

| 기능 | 사용 |
|---|---|
| F-11 제안서 생성·상세 | 4개 테이블 INSERT, 펼침 상세에 `detail`(판정 이유·대상)·근거 목록 |
| 제안서 머리 | 버전(`perimeter_version`.`seq`) · `created_at` · `trigger` · 기준 화선(`prediction_id → perimeter_id`) · `judged_stage`·`predicted_stage` |
| F-15 대응단계·격상 | 현재 단계 `judged_stage`, `predicted_stage`가 더 높으면 격상 대비 안내 |
| F-12 분류 | `axis`(진화·대피 탭), `categories`(구분 필터·건수) |

| F-13 근거 조회 | `citations` → `evidence_chunks`(문서·쪽·항목·본문), 어느 문장의 근거인지는 `proposal_items.text` |

### 2.5 제안 다루기

통합지휘권자가 AI 어시스턴트로 **묻거나(F-29 질의응답)** **상황 변화를 알리는(F-30 상황 정정)** 기능이다. 근거 조회(F-13)와 이력·변경 비교(F-14)는 2.4의 테이블로 처리한다.

| 테이블 | 1행 = | 내용 |
|---|---|---|
| `situation_corrections` | 확인·저장한 정정 1건 | 입력 원문, 바뀐 항목들(이전·이후) |
| `qa_messages` | 질문 1개와 답변 | 질문, 답변(근거 [k]), 지정한 항목 |

#### 상황 정정 — 무슨 말이든 받되, 바꾸는 칸은 정해져 있다

통합지휘권자는 자유롭게 입력한다. 하지만 제안서를 바꾸는 것은 규칙 엔진이 읽는 상황 값뿐이고, 그 값은 아래 **정정 가능 항목**으로 정해져 있다. AI는 자유로운 문장을 이 목록 안의 변경으로 바꾸는 역할만 한다. 목록에 없는 말은 저장하지 않는다.

| 대상 | 정정 가능 항목 | 저장 위치 | 규칙 엔진에서 |
|---|---|---|---|
| 마을 | 대피 완료 · 대피명령 | `incidents.situation.villages` | E2·E3 |
| 진화자원 투입 수 | 인력과 `resources`에 없는 헬기·장비(군·경찰 등) 수(합계와 기관·종류별, 산림청 상황 보고 양식). 헬기·차량 투입은 자원 관리(F-31)에서 산불에 연결(11/6) | `incidents.situation.deployed` | S3 · S7 |
| 전파 | 재난문자 송출 | `incidents.situation` | E6 |

- 진화예상시간은 넣지 않는다(1.3의 5번)
- 자주 나오는 말이 생기면 정정 가능 항목을 하나 추가해 넓힌다. 상황·변경이 jsonb라 테이블은 바뀌지 않는다
- 확인되지 않은 자유 문장(「현장 메모」)을 LLM에 넘기지 않는다. 판정은 규칙 엔진이 하고 LLM은 그 값을 바꾸지 못한다는 원칙 때문이다

| 입력 예 | AI 해석 | 결과 |
|---|---|---|
| 「괴산리 주민 다 빠져나갔어」 | 마을 1024 · 대피 완료 · false → true | 확인 카드 → 저장 |
| 「헬기 두 대 더 왔어」 | 헬기 투입 수(합계) · 28 → 30 | 확인 카드 → 저장 |
| 「확산대응 1단계 발령됐어」 | 정정 항목 아님(대응단계는 시스템이 판정) | 저장 안 함. 「대응단계는 화선·기상으로 판정합니다」 |
| 「바람이 세졌어」 | 정정 항목 아님 | 저장 안 함. 「기상은 다시 예측하면 반영됩니다」 |
| 「현장 분위기가 안 좋아」 | 정정 항목 아님 | 저장 안 함. 「정정할 수 있는 항목이 아닙니다」 |
| 「괴산리 대피 몇 시까지 해야 해?」 | 질문 | 질의응답(`qa_messages`) |

#### `situation_corrections` — 상황 정정

**어떤 테이블**: 확인 카드에서 **「확인」을 누른 정정 1건 = 1행**. 한 번 입력으로 여러 항목이 바뀌어도(「괴산리 대피 완료, 헬기 2대 추가」) 1행이다. 정정 1건이 제안서 새 버전 1개가 되기 때문이다(`proposals.correction_id`).

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | bigint | PK | |
| `incident_id` | bigint | NN, FK → `incidents` | |
| `user_id` | bigint | NN, FK → `users` | 정정한 통합지휘권자 |
| `input_text` | text | NN | 입력 원문. AI가 잘못 해석했는지 확인할 때 본다 |
| `changes` | jsonb | NN | 바뀐 항목들(아래). 정정 가능 항목만 들어간다 |
| `created_at` | timestamptz | NN, 기본 now() | 「확인」을 누른 시각 |

`changes` 형태:

```json
[
  { "target": "village", "target_id": 1024, "item": "evacuated", "before": false, "after": true },
  { "target": "deployed", "item": "helicopter.total", "before": 28, "after": 30 }
]
```

- 요구사항 분석서는 바뀐 항목마다 1행이었지만, 정정 1건 = 제안서 버전 1개라서 입력 1건 = 1행으로 묶었다
- 취소, 대상을 찾지 못함, 가용 범위 초과(예: 보유보다 많은 헬기 투입)는 아무것도 저장하지 않는다(UC-QA-02 A1·E1·E3). 가용 범위 확인에는 `resources`(2.6)를 쓴다

#### `qa_messages` — AI 질의응답

**어떤 테이블**: **질문 1개와 그 답변 = 1행**(1.3의 2번: 질문·답변만 저장). 질의응답은 상황과 제안을 바꾸지 않는다.

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | bigint | PK | |
| `incident_id` | bigint | NN, FK → `incidents` | |
| `user_id` | bigint | NN, FK → `users` | 질문한 통합지휘권자 |
| `proposal_id` | bigint | FK → `proposals` | 질문할 때 보고 있던 제안서. 예측 전이면 NULL |
| `item_code` | varchar(10) | | 「이 항목 질문」으로 지정한 항목. 없으면 NULL |
| `question` | text | NN | 질문 |
| `answer` | text | NN | 답변. 근거 번호 [k] 포함 |
| `created_at` | timestamptz | NN, 기본 now() | |

- 답변 속 [k]는 `citations.message_id`로 근거 청크를 가리킨다
- 질문마다 따로 답한다(앞 질문을 이어 받는 여러 턴 대화는 MVP에서 하지 않음)
- 근거를 찾지 못하면 추측하지 않고 「근거를 찾지 못했습니다」로 답하고 `event_logs`에 남긴다(UC-QA-01 E1)
- 정정으로 판별된 입력은 여기에 저장하지 않고 확인 카드로 넘긴다. 확인하면 `situation_corrections.input_text`에 남는다
- 빠른 질문 6개는 화면의 고정 문구라 저장하지 않는다

**데이터가 쌓이는 방식**

- 정정 「확인」 → 한 트랜잭션으로 `situation_corrections` 1행 INSERT + `incidents.situation` UPDATE + `event_logs`(`SITUATION_CORRECTED`)
- 이어서 현재 예측 그대로 규칙 판정·제안 생성 → `proposals`(`CORRECTION`, `correction_id`) 새 버전
  - **제안 생성이 실패해도 정정은 남는다**(UC-QA-02 E2). 마지막 정정 시각 > 현재 제안서 시각이면 화면에 「제안서가 최신 상황을 반영하지 못함 · 다시 생성」을 띄운다
  - **예측 전**(제안서 없음)에 한 정정은 상황만 저장하고 제안서는 만들지 않는다. 다음 예측 때 반영된다
- 질문 → 답변을 받으면 `qa_messages` 1행 + `citations`
- 고치거나 지우지 않는다. 종료된 산불은 정정을 막고 질문만 받는다

**기능에서 쓰이는 곳**

| 기능 | 사용 |
|---|---|
| F-30 상황 정정 | `situation_corrections` INSERT, `incidents` UPDATE, 제안서 새 버전 |
| F-14 「제안 변경사항」 창 | `proposals.correction_id` → `changes`(무엇을 정정했는지) |
| F-29 AI 질의응답 | `qa_messages` INSERT, 답변 근거는 `citations` |
| F-29 「이 항목 질문」 | `qa_messages.item_code` |
| F-32 이벤트 로그 | `SITUATION_CORRECTED`, 근거 부족 |
| F-03 종료 | 종료 후 정정 차단 |

### 2.6 지도·자원

#### `admin_areas` — 행정구역

**어떤 테이블**: 시도·시군구·읍면동 1개 = 1행. 사용자 관할(`users`)과 산불 위치(`incidents`)가 가리키고, 지휘권 인계 판정(S6, 「둘 이상 시군구·시도에 걸치면」)에 쓴다.

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | bigint | PK | |
| `level` | `admin_level` ENUM | NN | `SIDO`(시도) · `SIGUNGU`(시군구) · `EMD`(읍면동) |
| `code` | char(10) | NN, UK | **법정동코드 10자리**. 예: 의성군 `4773000000`, 의성읍 `4773025000` |
| `name` | varchar(50) | NN | 예: 의성군, 안평면 |
| `parent_id` | bigint | FK → `admin_areas` | 상위 행정구역(읍면동 → 시군구 → 시도). 시도는 NULL |
| `neighbor_ids` | bigint[] | NN, 기본 `{}` | **인접 시군구** id 목록(경계가 맞닿은 시군구). 시군구 행에만 채우고 시도·읍면동은 `{}`. 적재할 때 경계로 한 번 계산(`ST_Touches`/`ST_Intersects`). 예: 의성군 = 안동시·청송군·군위군(대구)·구미시·상주시·예천군 |
| `geom` | geometry(MultiPolygon, 5179) | NN | 경계(SGIS 2025-2Q) |

- 코드는 SGIS 코드가 아니라 **법정동코드**로 통일한다. 마을(법정리)·리별 인구가 법정동코드로 연결되기 때문이다(1.4)
- **넣는 범위**: 시도·시군구는 **전국**(시도 17 · 시군구 약 250), 읍면동은 **의성 18 + 인근 리가 속한 읍면 43**(11/8, 인근 리의 `admin_area_id`용). P5·P8이 관할 밖 시군구(안동·군위 등)나 다른 시도에 걸치는지 알아야 하기 때문이다(LLM 입력 L-17, S6 지휘권 인계)
- `admin_areas.neighbor_ids`(인접 시군구: S6 동원 범위·L-17)·`facilities.sigungu_id`는 경계가 바뀌지 않는 한 고정인 바탕 값이라 적재 때 미리 넣는다(규칙 엔진이 매번 경계를 계산하지 않게). 군위군은 2023년 대구광역시로 편입되어 의성 산불이 군위로 번지면 시도가 2개(경북·대구)에 걸친다
- 산불 등록 때 `incidents.admin_area_id` = 발화 지점을 포함하는 `EMD` 행(`ST_Contains`)

- **노선 번호(`ref`)는 OSM 원본에서 유지한다** — 지도 레이어(`의성/도로.geojson`)에는 빠져 있어 적재 파일(`map_features.geojson`)을 만들 때 원본에서 다시 붙였다(11/7, 큰 도로 1,230구간 중 683). 번호가 없는 조각은 도로명으로 묶는다. 한 노선에 도로명이 여러 개라(912호선 = 의성사곡로·안신로·영남제일로 …) 구간을 노선 번호로 묶는다(E5)

- 선은 **꼭짓점 좌표 목록**(LineString)으로 저장된다. 도로 하나는 교차로·차로가 바뀌는 곳에서 여러 행으로 나뉘고, 이름 있는 도로는 구간마다 같은 이름이 붙는다(경북대로 68구간). 길이·면적은 저장하지 않고 `ST_Length`·`ST_Area`로 계산한다

**이름 없는 것 부르기** — 이름 없는 행이 많다(큰 도로 1,230구간 중 472, 임도 대용 거의 전부, 송전선·철탑 전부, 발전소 전부). 제안 문장에 쓸 이름은 **판정할 때 만들고 저장하지 않는다**. 같은 도로라도 불이 어디를 덮었는지에 따라 부르는 범위가 달라지기 때문이다

**E5 도로 통제는 「통제 구간」까지만 알려 준다** — 도로 통제는 경찰 · 한국도로공사가 하고 통제 지점도 그쪽이 정한다(p.83, 의성산불백서 p.218). 실제 통제선은 교차로·회차 지점·우회로 분기점이어야 해서 도로 연결망이 필요하다. 그래서 규칙 엔진은 **「어느 도로의 어느 구간에 언제 불이 닿나」까지만** 계산해 통합지휘권자가 **통제를 요청**하게 한다(규칙 엔진 설계 R-19)

|---|---|---|
| 어느 범위 | 이미 닿음(P0) ~ 5시간 안(P5). P6~P8은 넣지 않음(잠재 위험구역 주민의 대피 길) | — |
| 어느 도로 · 구간 | P0~P5와 겹치는 `road` 조각을 **노선 번호(`ref`, 없으면 도로명)로 묶고**, 끝이 맞닿은 조각을 한 줄로 이어 끊긴 덩어리 하나 = 구간 하나(`ST_LineMerge(ST_Union(...))`). 상행·하행 두 줄은 하나로 합침 | 912호선(의성사곡로) 상화리~업리 |
| 언제 | 구간에서 가장 이른 닿는 시각(이미 닿음 / 0시 + n시간) | 이미 닿음, 15:00 |
| 얼마나 | 범위 안 길이(km) | 2.4 km |
| 가까운 경찰서 | 구간에서 가장 가까운 `POLICE` 중 **경찰서**(지구대·파출소·치안센터 제외) | 의성경찰서 |

- **순서를 매기지 않는다** — 모두 통제 대상이고 어디부터 막을지는 사람이 정한다. 닿는 시각은 값으로만 넘긴다
- **요청 대상(경찰서 / 한국도로공사)은 정하지 않는다** — LLM이 도로 등급(`highway`)을 보고 매뉴얼(p.83·p.89·p.95)로 고른다
- 통제 지점·우회 경로는 제시하지 않는다(경찰·지휘권자 판단)
- 불이 의성 밖 도로에 닿으면 그 시군 경찰서가 가까울 수 있다 → **적재 때 인근 시군 경찰서 위치를 추가**한다

#### `resource_bases` — 진화자원 기지

**어떤 테이블**: 헬기·차량이 소속된 **기지 1곳 = 1행**(산림항공관리소, 소방 항공대, 지자체 임차 계류장 등). 「어디에 몇 대 있나」와 「관할 자원인가 응원 자원인가」를 알기 위해 둔다. 기지는 고정된 곳이라, 자원의 실시간 위치를 추적하지 않는다는 결정(1.4)과 충돌하지 않는다.

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | bigint | PK | |
| `name` | varchar(100) | NN, UK | 예: 안동산림항공관리소, 의성군 임차 계류장, 경북 119 항공대 |
| `org_type` | varchar(20) | NN | 어느 기관 자원인가: `forest`(산림청) · `fire`(소방) · `local_lease`(지자체 임차헬기) · `local`(지자체 산불전문예방진화대 등) 등. 지원 요청 대상 기관을 정한다 |
| `geom` | geometry(Point, 5179) | | 기지 위치. 발화 지점에서 가까운 기지 순으로 쓴다. **모르면 NULL**(지자체 임차 계류장은 아직 모름) |
| `coverage_area_ids` | bigint[] | NN, 기본 `{}` | 관할 지역(`admin_areas` id 목록, 시군구 또는 시도). 예: 안동관리소 = 대구 + 경북 안동·영주·…·군위·의성·청송, 의성군 임차 = 의성군 |

- **관할 자원 판정**: 산불의 시군구(또는 그 시도)가 기지의 `coverage_area_ids`에 들어 있으면 관할, 아니면 응원. 지역이 바뀌어도 그대로 동작한다(지역 독립)
- 배열이라 외래키로 묶이지 않는다. 기지 수가 적고(전국 수십 곳) 전산 관리자만 고치므로 MVP는 배열로 둔다
- 산림청 관리소 13곳은 이름·주소·좌표·관할 권역을 받아 두었다(데이터 자원 D-40, `원본/산림청_산림항공관리소_20261029/`). 관할 권역은 적재 때 이름 → `admin_areas` id로 바꾼다(전국 시군구 적재, 11/6). 시도가 바뀐 군위군(2023 경북 → 대구)은 이름만으로 찾는다
- 기지가 없으면 나중에 전산 관리자가 추가한다(자료가 없는 기지는 이름·관할만 넣고 위치는 비워 둔다)

#### `resources` — 진화자원

**어떤 테이블**: 진화자원 **헬기·차량 1대 = 1행**. 어느 기지 소속인지와 **상태만** 둔다. 실시간 위치는 추적하지 않고, 진화대(인력)는 개별로 관리하지 않는다(1.4, 7주차-1차 회의). 전산 관리자가 등록·수정·삭제한다(F-31).

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | bigint | PK | |
| `kind` | `resource_kind` ENUM | NN | `HELICOPTER`(헬기) · `VEHICLE`(차량) |
| `name` | varchar(50) | NN, UK | 호기·차량 이름. 예: `FPA209`, `경북119-1` |
| `base_id` | bigint | NN, FK → `resource_bases` | 소속 기지 |
| `status` | `resource_status` ENUM | NN, 기본 `AVAILABLE` | `AVAILABLE`(대기) · `DEPLOYED`(투입) · `MAINTENANCE`(정비) |
| `deployed_incident_id` | bigint | FK → `incidents` | **투입된 산불**(11/6). `status = DEPLOYED`일 때만 값이 있고, 그 밖에는 NULL(CHECK). 관리자가 자원을 산불에 연결한다(F-31) |
| `attrs` | jsonb | NN, 기본 `{}` | 자원의 특징(아래). 예: `{"model": "S-64E", "capacity_l": 8000}` |

- 소속 기관·관할은 기지에 있으므로 자원마다 반복하지 않는다
- **특징은 `attrs`(jsonb)에 둔다**: 헬기 `model`(기종)·`capacity_l`(담수량 L), 차량 `vehicle_type`(진화차·펌프차·물탱크차 등)·`capacity_l`. 종류마다 특징이 다르고 판정에 꼭 쓰는 값이 아니라서 칸으로 두지 않는다(`facilities`·`map_features`와 같은 방식). 관리 화면 표시에 쓰고, 나중에 「대형 헬기 우선 투입」처럼 판정에 쓰게 되면 그때 키를 정해 읽는다
- `attrs.vehicle_type` 값: 소방 `펌프차` · `물탱크차` · `산불전문진화차(대형)` · `산불전문진화차(소형)`, 산림청·지자체 `산불진화차` · `산불지휘차` · `고성능진화차`(국회입법조사처 산불대응연구TF 특별보고서 표 4의 차종)
- 가정값 여부는 DB에 두지 않고 적재 파일(`assumed`·`basis` 칸)과 데이터 폴더 README에 남긴다
- **헬기·차량의 산불별 투입은 `deployed_incident_id`로 센다**(1.3의 4번, 11/6). 규칙 엔진 S3는 「투입」 = 이 산불에 연결된 자원, 「부를 수 있음」 = `AVAILABLE` 자원으로 센다. 다른 산불에 나간 자원·정비 중인 자원은 자연스럽게 빠진다. 인력과 `resources`에 없는 자원(군·경찰 헬기 등)은 `incidents.situation.deployed`에 숫자로 둔다
- 시연: 적재 데이터에 투입 상태(`DEPLOYED` + `deployed_incident_id`)를 미리 넣는다. 관리 화면의 상태 변경(F-31)은 FastAPI 단계에서 만든다
- 다른 테이블이 자원 id를 가리키지 않으므로(투입 수는 숫자) 삭제는 행을 지운다. 등록·수정·삭제는 `event_logs`에 `RESOURCE_UPDATED`(자원 id, 변경 전후 값)로 남는다

**데이터가 쌓이는 방식**

- `admin_areas`·`villages`·`facilities`·`map_features`: 적재 파일을 한 번 넣는다(좌표는 4326 → 5179로 변환). 데이터를 다시 만들면 통째로 바꾼다. 서비스 중에는 바뀌지 않는다
  - 다만 `villages.id`·`facilities.id`는 `incidents.situation`·`proposal_items.detail`이 가리키므로, 다시 넣을 때 **`code`(마을)·이름+위치(시설)로 기존 id를 유지**한다
- `resource_bases`·`resources`: 시연값을 한 번 넣고, 이후 전산 관리자가 화면에서 등록·수정·삭제한다
