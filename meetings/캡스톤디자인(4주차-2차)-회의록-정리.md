## 🔑 핵심 결론 (이번 회의의 본질)

**'누가'와 '무엇'이 이번 회의로 모두 확정됐다.**

- **누가** = 기관이 아닌 **개인 1인**: 초기대응·확산대응 1단계의 **시장·군수·구청장**(통합지휘본부장 겸 주민대피 명령권자, p.72, p.84)
- **무엇** = **의사결정 항목 14개**(진화 S1~S7 + 대피 E1~E7)를 고정 형식의 제안서로 제시
- 지원 체계로 **정보 사전**(1차: 원천 데이터 / 2차: P5 연산 산출물)과 **출력 계약**(블록 14개 고정 + JSON 스키마)까지 설계 확정

> **한 줄 요약:** 서비스는 "확산예측 폴리곤(P5/P8)을 입력받아, 시장·군수·구청장 1인에게 14개 의사결정 항목을 매뉴얼 근거와 함께 고정 형식으로 제안하는 시스템"으로 확정됐고, 남은 것은 화면(HTML 시안)과 SC-1a 렌더링 예의 구체화다.

## 3. 안건별 논의 요약

**① 서비스 대상 (기관별 vs 개인)**
- 논의: 기관별로 갈지, 개인(지자체장, 통합지휘실 책임자)으로 갈지 논의.
- 결론: **합의** — **개인**을 서비스 대상으로 확정. 근거: 추론 및 매뉴얼 검증까지 진행 가능하고, 조금 더 구체적인 임무를 전달할 수 있음. 구체적으로는 초기대응·확산대응 1단계의 시장·군수·구청장 1인(통합지휘본부장 겸 주민대피 명령권자, p.72, p.84).

**② 의사결정 항목 정리**
- 논의: 책임자 1인에게 제안해야 하는 의사결정을 대분류 2개(진화·대피), 소분류 14개(S1~S7, E1~E7)로 정리. 각 항목에 제안 이유·매뉴얼 근거(쪽수)·권한(직접/협의/요청)·필요정보(1차/2차)를 매핑.
- 입력 가정: 확산예측 결과 **P5(5시간 확산 범위 폴리곤, 필수)** + **발화점·현재 화선 F0**. **P8(8시간 폴리곤)은 권장** — 매뉴얼의 "실행 대기" 구역(p.74~76)은 P8이 있어야 산출됨.
- 결론: **합의** — 부록 A의 표대로 확정.

**③ 정보 사전**
- 논의: 1차 정보(전처리 없이 쓰는 원천: 입력 폴리곤·정적 공간 레이어·동적 관측·현장/상황실 입력 4개 묶음)와 2차 정보(P5와 레이어의 연산 산출물)로 2층 구조화. 항목별 출처·확보 상태 점검.
- 결론: **합의** — 부록 B대로 확정. 단, 확보 상태 "확인 필요/요청 필요/비공개 가능" 항목은 미결로 이월(§6).

**④ 출력 계약**
- 논의: 제안서를 헤더 1 + 항목 블록 14(순서 S1~S7·E1~E7 고정, 생략 불가) + 요약 1로 고정. 블록마다 판정/구분/제안/대상/충돌/근거 6줄 고정, 구분 토큰 어휘 고정(즉시·대기·협의·요청·보고·근거 부족·정보 부족·생성 실패·(없음)). 오케스트레이터 최종 출력은 JSON 스키마(items 길이 14 고정).
- 결론: **합의** — 부록 C대로 확정. 단, 렌더링 예(SC-1a)는 **초안**이라 대폭 구체화 필요.

### P1 — 토요일(9/26) 기능 회의에서 결정

- **서비스 기능 목록** — HTML 시안 취합 후 토요일 21시 회의에서 확정
- **제안서 생성·갱신 방식** ※ — 스펙이 이미 여러 번 생성을 전제(S1·S3·S4 "시점마다", E1 "갱신될 때마다", JSON의 `t0`·`run_id`). 선택지: ⓐ 수동 트리거(단, 새 입력을 넣을 실제 운영자가 없음) ⓑ 주기 자동 재생성(확산예측 재실행 주기마다) ⓒ 이벤트 기반(새 P5 도착 시, P5 인터페이스 합의 선행). 어느 안이든 후속 결정: 갱신 주기, 데모의 시간 진행 방식(가속·타임라인), D 묶음 입력 필드의 처지(시나리오 주입 vs 시연 중 변경), 이전 run 대비 diff 표시 여부. HTML 시안 전제와 직결되므로 우선 결정 필요.
- **데모 지역·시나리오 세트** ※ — ✅ **결정 완료.** 데모 지역 확정됨(지역명 추후 기재 — SC-1a 예시상 강릉시 옥계면으로 추정, 확인 필요). 남은 것: 시나리오 개수.

### P2 — SC-1a 구체화·설계 작업과 함께 결정
- **SC-1a 렌더링 예 구체화** — 초안 상태 (액션 아이템)
- **충돌 유형·트리거 조건 규칙표** ※ — 규칙 엔진 구현에 필요한 규칙표 2개가 아직 없다.
  - **① 트리거 조건표 (14개 항목별 발동 조건):** 출력 계약상 조건이 충족되지 않은 항목은 "(없음) = 트리거 미발동"으로 출력된다(SC-1a에서 S6·E3·E7이 (없음)인 이유). 그런데 각 항목이 **언제 발동하는지**가 문서화돼 있지 않다. 예시에서 역산하면 "E1: 마을 ∩ P5 ≥ 1", "S5: P5 내 보호대상 시설 ≥ 1", "E7: 고립 후보 ≥ 1 또는 부상 보고 존재" 식일 텐데, 이런 조건을 14개 전부 명시해야 규칙 엔진을 구현하고 (없음) 판정을 재현할 수 있다.
  - **② 충돌 유형표 (유형 목록 + 감지 조건 + 처리 방향):** 충돌 줄의 예시가 "② 대피로·진입로 겹침(관련 S3) / 처리 방향: 요청 전환" 하나뿐이다. 번호 ②가 붙어 있어 ①·③… 유형 목록이 전제돼 있으나 그 목록이 없다. 항목 간 제안이 부딪히는 경우 — 예: 대피 경로와 진화차량 진입로가 같은 도로(E5↔S3), 같은 소방차를 시설 보호(S5)와 진화 구역(S3)에 동시 요구, 배정한 대피소가 다음 갱신에서 P8에 포함(E4) — 를 유형으로 나열하고, 유형별 감지 조건과 처리 방향(어느 쪽 우선·요청 전환 등)을 정해야 JSON의 `conflicts {type, with, resolution}` 필드를 채울 수 있다.
- **데이터 확보 상태 확인** (부록 B 기준)
  - P8·P1~P5 슬라이스: 확산예측(5.3.1) 측에 요청 필요, P5 인터페이스 합의 필요
  - 행정리(마을) 경계: 공개 여부 확인 필요
  - 한전 송전선·변전소, 군사·가스·유류 시설: 비공개 가능성
  - 기상청 API 키 발급, 산림항공관리소 위치, 대피소의 산불 지정대피소 여부(지자체 확인)
  - 보유 자원·인접 기관 가용 자원: 부록 미확보라 시나리오값 사용

### P3 — 명세서에 '미결(결정 예정)'로 명기, 구현 전까지 결정
- **매뉴얼 근거가 없는 산출 로직** — 진화 난도(국립산림과학원 자료 참고 필요), 헬기 운용 임계값(풍속·시정·야간), 자원 수량 산식(순서까지만 제안, 수량은 "근거 부족" 표기 방침)

# 부록 C. 출력 계약 (고정 형식)

## C-1. 형식 규칙
- 제안서는 항상 **헤더 1개 + 항목 블록 14개 + 요약 1개**로 구성한다. 항목 블록 순서는 S1, S2, …, S7, E1, …, E7로 고정하며 해당 없는 항목도 블록을 생략하지 않는다.
- 블록마다 여섯 줄이 고정 순서로 나온다: **판정 / 구분 / 제안 / 대상 / 충돌 / 근거**. 값이 없는 줄은 "(없음)"으로 채운다.
- 판정 줄은 규칙 엔진 결과이므로 항상 값이 있다(트리거 미발동이면 그 사실을 적는다). 구분·제안·대상은 A4가, 충돌은 A3가, 근거는 검색 메타데이터가 채운다.
- 근거 줄의 [k] 번호는 항목 안에서 1부터 매기며, 제안 줄의 [k]와 같은 번호를 가리킨다. 전역 각주는 두지 않는다.
- 구분 줄의 어휘는 고정이다. 여러 개면 "즉시 / 대기"처럼 아래 순서로 나열한다.

| 구분 토큰 | 뜻 |
|---|---|
| 즉시 | 책임자 권한, 지금 시행 |
| 대기 | 책임자 권한, 조건 충족 시 시행 |
| 협의 | 발령권자(산림청장)와 협의 |
| 요청 | 타 기관에 요청(대상 줄에 기관명) |
| 보고 | 상급 본부 보고 |
| 근거 부족 | 질문은 생성됐으나 청크에 근거가 없음(부분 부족은 제안 줄 문장으로 표기) |
| 정보 부족 | 필수 입력 필드 결측으로 답변 생략 |
| 생성 실패 | LLM 오류 후 재시도 실패 |
| (없음) | 트리거 미발동, 이번 상황에서 해당 없음 |
