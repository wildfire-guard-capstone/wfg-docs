# **캡스톤디자인(3주차) 피드백 정리**

### 2026학년도 2학기 · 캡스톤디자인 2분반 · 3주차(수정 과제 계획서 발표 + 요구사항 분석 강의)

## **1. 공통 피드백**

### **1-1. 권기학 교수님**

- 표지에 일시, 팀명, 지도교수, 팀장, 팀원을 모두 넣는다. 1조 표지를 예시로 들며 다른 팀도 참고하라고 지시했다.
- 장표마다 페이지 번호를 적는다. 페이지 번호를 적지 않은 팀이 있었다.
- 발표자료 앞부분에 지난 피드백 정리 장표를 배치한다. 교수 피드백 → 기존안 → 수정·보완 내용 순으로 정리하면 분석을 충실히 했다는 인상을 준다. 사회에 나가 발표할 때도 같은 방식으로 정리하라고 강조했다.
- 목표 장표는 정량적 목표 항목과 정성적 목표 항목을 나열하고, 항목별 목표치와 설정 근거를 오른쪽에 붙이는 형태로 작성한다.
- "목표는 문장이 아니라 숫자로 검증한다"와 같은 선언적 문구를 목표 장표에 넣지 않는다. 중심 내용인 목표 항목이 가려져 문서의 핵심이 흐려진다.
- 수정한 부분만 발표하더라도 목표 항목 자체가 무엇인지는 드러나야 한다.
- 제출한 워드·한글 문서에 제대로 작성되어 있더라도 발표 장표가 다른 구성으로 되어 있으면 안 된다. 두 문서의 구성을 일치시킨다.
- AI를 활용하는 것은 좋으나 사용 사실을 반드시 문서에 명기한다.
- 기업 과제 팀은 작성한 계획서를 교수에게 제출하는 동시에 기업에도 보내 의견을 받아온다. 앞으로 기업 과제 산출물은 모두 이 절차를 따른다.
- 간트차트 왼쪽 업무를 상위·하위로 그루핑해 1, 1-1 형태의 계층으로 나눈다.
- 현장 담당자에게 직접 연락해 문제를 정의하는 접근을 "아주 바람직합니다"라고 평가했다. (1조 사례에 대한 평가로, 모든 팀에 대한 요구로 명시하지는 않음)

### **1-2. 문현준 교수님**

- 팀별 고정 IP를 제출한다. 5개 팀 것이 모두 모이면 AI(GPU) 서버에 등록한 뒤 계정을 회신한다. 아직 보내지 않은 팀은 당일 중으로 보낼 것.
- 경진대회에서 데모를 해야 하므로, 최종 화면(GUI)에서 무엇을 보여줄지를 지금 단계에서라도 계획에 담는다. 아직 초기 단계라 확정적이지 않아도 된다. 발표 중 "다른 팀도"라고 명시했다.

## **2. 5조 발표 QnA**

**Q. 대응 방안을 제시하는 시스템인데, 실제 인력이나 장비까지 고려해서 임무를 부여하는 것인가? (참석자)**

**A. **맞다. 공무원 역할에 해당하는 부분에서 인력·장비 관련 사항을 도맡아 처리하도록 설계했다.


**Q. Ablation 평가에서 구체적으로 어떤 기능을 빼고 무엇과 비교할 것인가? (참석자)**

**A. **RAG를 적용했을 때와 적용하지 않았을 때의 성능을 비교하는 방식으로 진행한다.


**Q. 지금 산불을 예측하는 시스템이 어디에 있는가? 5조 과제도 예측 시스템 아닌가? (권기학 교수님)**

**A. **국가 차원의 예측 시스템이 이미 존재한다. 5조의 중점은 예측이 아니라 근거를 기반으로 공무원·진압대원·소방대원이 수행할 임무를 자동으로 도출하는 것이며, 확산 예측은 오픈소스 모델(ELMFIRE)을 가져다 쓰기로 결정했다. 

→ 다만 교수님은 차별성 장표에 제시된 기존 시스템 기능이 개념 수준에 머물러 있으므로 더 구체적인 수준까지 조사해 비교하라고 요구했다.


**Q. LLM을 쓰고 있는데 VLM을 쓸 계획은 없는가? (문현준 교수님)**

**A. **기존 확산 예측 연구에서는 CCTV 영상으로 발화 위치를 파악하는 데 VLM을 사용한다. 그러나 5조 시스템은 확산 예측 이전 단계의 입력을 이미 받는다는 가정이므로, 예측 데이터를 바탕으로 소방·구조요원·공무원의 임무를 배치하는 것이 목표다. 따라서 LLM만 사용하고 VLM은 별도로 사용하지 않는다.


**Q. 사용하려는 데이터가 AI 허브가 아니라 공공데이터포털에 있는 것인가? (문현준 교수님)**

**A. **실시간 데이터는 기상청 API로 수집하고, 법령·근거 문서는 대외비가 많아 담당 주무관에게 직접 연락해 받을 예정이다. 확산 예측과 RAG에 필요한 나머지 데이터는 공공데이터포털, 정부가 직접 제작한 데이터셋, AI 허브 데이터를 함께 활용해 구축한다. 추가로 산림청에 시계열 데이터 확보를 문의했으나 담당관 부재로 다음 주에 다시 연락하기로 했다.


**Q. 고정 IP는 보냈는가? (문현준 교수님)**

**A. **아직 보내지 못했다. 빠른 시일 내로 제출하기로 했다.

## **3. 5조 피드백**

### **3-1. 권기학 교수님**

- 전반적으로 잘 작성되어 있다고 평가받았다.
- 피드백을 2장으로 정리해 앞에 배치한 구성은 다른 팀도 참고할 만한 좋은 사례로 언급되었다. 교수 피드백 외 추가 수정·보완 내용을 뒤에 따로 정리한 부분도 좋게 평가받았다.
- 차별성 장표의 기술 수준이 너무 개념적이다. "예측 결과 / 대응 문장 / 수작업", "역할별 산출 / 진화 / 대피 / 추적 없음" 정도로는 부족하므로, 기존 시스템(국가 예측 시스템 등)의 기능을 구체적인 수준까지 조사해 비교하고 그로부터 우리가 해야 할 일이 도출되게 한다.
- 기대효과가 효과가 아니라 항목 나열에 가깝다. "산업적 효과, B2G, 지자체, 산림청, GPU, 표준 판단" 식으로는 효과인지 판단할 수 없다. 산림청 입장에서는 어떤 효과가 있고 지자체 입장에서는 어떤 효과가 있는지 실질적 효과 중심으로 크게 적는다. 사회적 효과도 마찬가지다.

### **3-2. 문현준 교수님**

- LLM만 사용하고 있는데 VLM 활용도 한번 검토해 보면 좋겠다.
- 고정 IP를 아직 제출하지 않았다. 빠른 시일 내로 제출한다.

### **3-3. 청중 질의에서 도출된 보완 사항**

- 임무 부여 시 실제 인력·장비를 어떻게 반영하는지 문서에 드러나게 한다.
- 산림청 시계열 데이터 확보 여부에 따라 예측 파트 계획이 달라질 수 있으므로 다음 주 연락 결과를 반영한다.

# **5. 요구사항 명세서 작성 강의 정리 (권기학 교수님)**

발표가 지연되어 이론 슬라이드는 대부분 빠르게 넘어갔고, 과제로 무엇을 어떻게 제출해야 하는지에 초점을 맞춰 설명했다. 강의 자료와 샘플은 모두 업로드해 줄 예정이므로 세부 내용은 자료로 확인하면 된다.

### **5-1. 요구(Requirements)의 개념**

- 요구는 크게 두 가지다. 고객·기업이 요구하는 것(비즈니스 요구)과 시스템이 요구하는 것(시스템 요구).
- 발표 중 나오는 "고객이 어떻게 생각하는지", "그 기능이 어떻게 동작해야 하는지" 같은 질문 자체도 요구사항에 해당한다.
- 요구는 시스템에 대한 고객의 요청을 확정한 것이며, 진정한 요구를 찾는 일이 프로젝트 성공의 필수 조건이다.
- 이해관계자(stakeholder)를 먼저 파악한다. 학사정보시스템이라면 학생(고객), 교수, 행정 담당자, 예비 입학자와 학부모가 모두 이해관계자다. 이들이 어떤 내용을 필요로 하는지 조사하고 제약사항을 파악해야 한다.
- 요구 분석은 현재(as-is) 시스템에서 목표(to-be) 시스템으로 옮겨 가는 과정이다.

### **5-2. 요구의 분류 — 기능 / 비기능**

- 기능 요구사항 외의 모든 것이 비기능 요구사항이다. 제약사항, 법적 사항, 성능, 응답 속도, 데이터, 인터페이스 등이 모두 비기능에 해당한다.
- 예: 인터넷 쇼핑몰에서 상품 검색·장바구니·상품 주문·마일리지는 기능 요구, 반응 시간·정보 보호·데이터 복구·처리량은 비기능 요구다.
- **AI 과제는 비기능 요구사항이 특히 중요하다.** 비기능 요구사항 중에서도 AI 쪽은 따로 구체적으로 도출해서 적을 것.

### **5-3. 요구 추출 방법**

- 고객의 발표, 문헌·양식 조사, 인터뷰, 설문, 브레인스토밍 회의, 관찰과 작업 분석, 프로토타이핑.
- 레거시 시스템(기존에 쓰고 있는 시스템, 예: 학사정보시스템의 기존 서버)도 정보 출처가 된다.
- 예시로 든 학사정보시스템에서는 학생에게 수강신청의 불편(정원 부족, 접속 지연 등)을 듣고 교수에게도 들어 요구사항을 수집하는 식으로 진행한다.

### **5-4. 요구 분석 = 세 가지 모델링**

| 모델링 | 산출물 | 성격 |
| --- | --- | --- |
| 기능적 모델링 | 유스케이스 다이어그램 | 사용자와 환경 관점에서 기능을 명확히 도출 |
| 정적(구조적) 모델링 | 클래스 다이어그램 | 데이터 구조 관점 |
| 동적 모델링 | 시퀀스 다이어그램 | 인터페이스, 객체 간 상호작용 순서 |

- 이 세 가지 모델링을 하면 만든 시스템이 기본적으로 작동할 수 있는 수준이 된다. 명목상 요구사항 단계지만 실질적으로는 설계의 기본이 완성되는 단계로 보면 된다.
- 시퀀스 다이어그램은 입력단이 있으면 반드시 출력단이 있어야 한다.
- 일부 팀은 이미 유스케이스 다이어그램이나 UI 프로토타입을 그려 왔는데, 그 절차대로 진행하면 된다.

### **5-5. 유스케이스**

- 구성 요소: 액터(actor), 유스케이스, 관계, 시스템 범위.
- 액터는 사용자뿐 아니라 다른 시스템도 될 수 있다.
- 예: 수강신청 시스템에서 학생은 수강신청·취소·과목 열람 유스케이스를 가지고, 교직원·교수도 각자의 유스케이스를 가진다.
- 관계는 포함과 확장 두 가지다. 결제 시 고객 인증이 반드시 필요한 경우는 포함 관계, 결제 시 멤버십 확인으로 할인을 적용하는 경우는 확장 관계다.
- 유스케이스 명세서(시나리오)는 개요, 행위자, 선행·후행 조건, 기본 흐름, 대안 흐름, 예외 흐름으로 작성한다. 예시로 든 인터넷 쇼핑몰의 카테고리등록 유스케이스는 "1. 최상위 카테고리 목록을 관리자에게 보여준다 → 2. 관리자가 조회한다" 식으로 흐름을 기술하고, 안 될 때의 대안 흐름과 예외 흐름을 덧붙인다.
- 문제설명서(상황설명서, 시스템 기술서)에서 액터와 기능을 먼저 정의하면 그것을 바탕으로 유스케이스 다이어그램과 시퀀스 다이어그램을 만들 수 있다.

### **5-6. 요구사항 명세서 구성**

- 국제 기준인 IEEE 830 목차를 참고하되, 반드시 그대로 따라야 하는 것은 아니다. 하드웨어 등도 포함해 작성할 수 있다.
- 요구사항 명세서의 형태는 다양하고 프로젝트 특성에 따라 차이가 크다. **이번 학기 프로젝트는 기술 개발 성격이므로 강의 교안과 다르게 테일러링(재단)해서 작성하는 것이 바람직하다.**
- IEEE 830 목차만 그대로 옮겨 제출한 학생이 있었는데, 요구하는 것보다 다소 부족하다는 느낌을 준다.

**요구사항 명세서 작성 시 필수 포함 사항**

1. 문제설명서(업무 절차기술서)
2. 유스케이스 다이어그램
3. 유스케이스 시나리오(설명서, 명세서)
4. 유스케이스 식별자 목록
5. 클래스 다이어그램
6. 관계형 데이터베이스
7. 시퀀스 다이어그램
8. 속성 정의
9. 오퍼레이션 정의
10. 관계 정보
11. 비기능 요구사항(HW, 인터페이스, 성능, 품질, 기타)

### **5-7. 발표 구성 및 제출 안내**

발표는 다음 순서로 구성한다. 청중이 과제를 모를 수 있으므로 프로젝트 계획서를 짧게 먼저 소개한 뒤 요구사항 분석 내용으로 들어간다.

1. 프로젝트 계획서 발표(개요, 동기, 시스템 구성도, 기능, 기대효과 등) — 짧게
2. 프로젝트 유스케이스 모델링 — 문제 설명서(업무 절차 기술서)
3. 유스케이스 다이어그램 (시나리오 작성 → 다이어그램 작성 → 식별자 목록 작성)
4. 클래스 다이어그램 (다이어그램 작성 → 속성 정의 → 오퍼레이션 정의 → 관계 정보)
5. 시퀀스 다이어그램
6. 비기능 요구사항(HW, 인터페이스, 성능, 품질 요구사항 등)

- 제출: 집현캠퍼스에 14:00까지 제출한다.
- 파일 형식: `X조_주제명_요구사항분석서_팀장명`
- AI를 활용했다면 반드시 명기한다.
- 샘플 2종(기업 과제용 요양기관 플랫폼 요구사항분석서, 안구질환 과제 요구사항분석서)을 업로드해 줄 예정이니 참고해 작성하면 된다. 두 샘플 모두 수정본이며, 프로토타입은 포함되어 있지 않다. 기업 과제 팀은 요양기관 플랫폼 샘플을 참조한다.
- 샘플은 목차 → 프로젝트 개요 → 문제 설명서(시스템 기술서) → 주요 기능 → 유스케이스 다이어그램·시나리오 → 클래스·시퀀스 → 비기능 요구사항(AI 부분은 별도로 도출) 순으로 구성되어 있다.

### **5-9. TOPCIT 시험 관련 언급**

- 액티비티 다이어그램, 유스케이스 다이어그램은 시험에 나올 수 있다. 클래스 다이어그램도 출제 범위에 든다. 시퀀스 다이어그램은 거의 출제되지 않는다.
- 캡슐화·연관·상속·다형성은 공무원 시험에 가끔 출제되므로 알아 둘 것.

- 공학설계기초 수강생은 이미 다룬 내용이다.
